### v0.9.60-certio-obf（2026-11-25）当前版

**证书读取的 I/O 全部改内联 svc + 加 8 级诊断**

#### 背景（v0.9.59 的 -13 定位到这一步）
rc 透传后真因是 **-13 = 证书读不出**（不是 -12 定位失败）。而
`ncg_apk_first_cert_der` 用的是 libc `open/fstat/pread` —— 全是
「去签名校验」工具 hook 的目标。

#### 改动
① `nc_guard_paths.c` 新增 `ncg_apk_open_ro/pread/fsize/close`
   （内联 svc，双 ABI；armv7 的 pread 偏移按 32 位截断并断言）。
② `nc_guard_key.c` 改用它们，**且用弱符号 + libc 回退**：
   - 生产构建（整包编译）：paths.c 提供实现 → 走内联 svc
   - V11a/V13c 跨语言对拍驱动（只链 key.c）→ 弱符号 NULL → 回退 libc
   ⚠️ 不能直接 include internal.h（会拖进 ncg_trace 实现 → 对拍驱动链接失败，
      实测 V11a/V13c 立刻红）。所以追踪也走弱符号回调 `ncg_key_trace[_i]`，
      由 boot.c 在文件末尾提供实现并映射到真正的 NCG_TR_*。
③ 新增 8 条诊断：CERT 打开失败 rc / fd / 文件大小 / 无 EOCD / CD offset /
   无 footer / magic 不匹配 / 签名块大小 —— 下次 -13 能直接看到是哪一步。
④ 顺手清掉 report.c 两处既有 `-Wunused-variable`（与本次无关但挡 -Werror）。

test.sh 55/0；双 ABI 8 文件编译通过。

### v0.9.59-rctrans-obf（2026-11-25）

**修 rc 被吞：`return -12` 写死，让 -13/-14 细分形同虚设**

#### 现象（诊断日志揭穿，排查三天）
```
U1-A OK maps 命中 =/data/app/.../base.apk   ← APK 定位成功
U12 FAIL k_so 派生失败                        ← 但报 -12「定位不到 APK」
```
两条互相矛盾：定位明明成功了。

#### 根因
`ncguard_unlock` 里：
```c
if (ncg_derive_kso_bound(...) != 0) {
    ncg_trace(NCG_TR_U12_FAIL);
    return -12;          // ← 写死！把 -13/-14 全吞成 -12
}
```
v0.9.53 给 `ncg_derive_kso_bound` 细分了 -12/-13/-14（定位/证书/包名），
但调用方写死 -12 → **细分完全无效**，日志一直把排查方向引向"定位"，
实际是"读证书"。这是"改了产出侧没改消费侧"的典型。

#### 修复
透传 `krc`，并加 `U12 FAIL rc 值` 追踪。上层 `ncg_death_notice`
现在能给出准确的 -13「证书读不出」/-14「包名对不上」。

### v0.9.58-mapsopen-obf（2026-11-25）

**修 maps 路里的 `open()` —— 去校验 hook 让它失败（真因，诊断日志定位）**

#### 诊断证据（v0.9.57 加的逐路追踪立功）
```
U1-A 尝试 maps 路
U1-A OK maps 命中 =/data/app/.../com.nivii.app-xxx==/base.apk   ← 路径正确！
U12 FAIL k_so 派生失败                                          ← 但整体仍 -12
```

#### 根因
`ncg_scan_maps_for_base_apk()` 在拿到候选路径后用
`int t = open(out, O_RDONLY); if (t >= 0) ...` 做最终验证。
而 **`open` 正是「去签名校验」hook 的 17 个函数之一**（libusign 把它
重定向到 `code_cache/sigfix-origin.apk`）。锁箱跑在 constructor(50)
（进程最早），此时 SigFix 还没释放 origin.apk → 重定向目标不存在
→ `open` 失败 → maps 路判失败 → 回退路也失败 → `-12` → 密文 SIGILL。

**这是我同一个纪律漏改的第二处**：v0.9.55 修了 `ncg_find_apk_path`
回退路的 `access`，但 maps 路里的 `open` 没查。AGENTS.md 早写明
「任何读自身 APK 的路径都必须内联 svc」。

#### 修复
改成 `ncg_apk_readable()`（内联 `__NR_faccessat`，不经 libc）。
另加 `U1-A maps 命中但路径不可读 rc` 追踪，下次若再失败能直接看到 rc。

### v0.9.56-apklocate2-obf（2026-11-24）

**修 v0.9.55 的静默失效：内联 svc 不能放 VMP 编译单元。**

#### 现象
v0.9.55 已修「回退路不验证候选路径」，但真机复测**仍然** `rc=-12` +
constructor SIGILL。产物反汇编显示 `.ncq`（VMP 字节码）从 95,397 涨到
108,693 B —— **我加的代码被 Amice 虚拟化了**。

#### 根因
`nc_guard_crypto.c` 在 `make-zip-lib.sh` 的 `_vmp=1` 名单里（整文件 VMP）。
v0.9.55 把 `ncg_raw_faccessat`（内联 svc）写在该文件 → 被 VMP 转换后
**`svc` 被当作普通操作码处理**，语义不再可靠 → 检查恒失败 → `-12`。

⚠️ 这是个**极易重犯**的坑：源码完全合法、双 ABI 编译通过、导入表里
`access` 确实消失了（因为 VMP 保留了一份 `.text` 内联副本）、宿主
test.sh 也全绿（宿主走 `#else` 的 libc 分支）—— 只有真机才能暴露。

#### 修复
把 `ncg_apk_readable()` 移到 **`nc_guard_paths.c`**（不在 VMP 名单 =
明文 `.text`），`ncg_find_apk_path` 改为调它。`noinline, used` 防内联/回收。

验证：`ncg_apk_readable` 是 `.text` 里的全局符号 `T`，反汇编含
`mov w2,#0x4`(R_OK) + `svc`；nox test.sh 55/0（V6 解锁/V7 常量表全绿）。

#### 教训（已写进代码注释）
**内联汇编/系统调用必须放不被 VMP 的编译单元。** VMP 的目标函数里
不能有 `asm`——VM 的语义里没有"执行一条 svc"这个概念。

### v0.9.55-apklocate-obf（2026-11-24）

**修 APK 定位在 extractNativeLibs=true 下的必崩缺陷**（真机事故：Nivii 1.0.9）。

#### 现象
注入「去校验 → 加固」后装机即 SIGILL，`pc` 落在 `libnc.so` 的 constructor
（`call_constructors+244`）。锁箱 trace 显示 U1~U10 全成功、**卡在 U12**：
`ncg_find_apk_path` 返回 -1 → `ncg_derive_kso_bound` 返 -12 → `.ncx` 不解
→ 执行密文。多路采集/防线日志一律没有（崩在 constructor，早于一切判定）。

#### 根因（两处叠加）
① **maps 路必失败**：`extractNativeLibs=true` 时 so 解压到 `lib/<abi>/`，
   `/proc/self/maps` 里**没有** `base.apk` 映射行。
② **回退路只拼字符串、从不验证**：`strstr(so_path,"/lib/")` 截断后拼
   `/base.apk` 直接 `return 0`。候选路径不存在也当成功 → 后续读证书 open
   失败 → -12。第一线 `sig_check.c` 的 `apk_locate_so_dir` 早就有
   `access(R_OK)` + `/proc/self/root` 前缀，**两条线不同步**。

#### 修复
① 回退路补**可读性校验**：`/proc/self/root` 前缀优先 → 原路径，逐个验；
   全失败返回 -1（fail-closed 明确 -12，不拿死路径掩盖真因）。
② 校验用 **内联 svc（`__NR_faccessat`）**而非 libc `access()`：后者是
   去签名校验工具 hook 的 17 个函数之一，用它会"校验通过但读到诱饵包"。
   与 artifact-pipeline 的契约一致（任何读自身 APK 的路径必须内联 svc）。
   armv7 的 r7 push/pop 已处理。

#### 验证
双 ABI 编译过；test.sh 55/0；最小编译单元导入表里 `access/faccessat`
**全部消失**（只剩 1 条 svc），证明内联生效。

⚠️ **未验证**：Nivii 原包（70MB，需重新加固+去校验）在真机上的复现修复
——留给用户验收（`ncguard_log.md` 的 U12 应变为 `U12 OK`）。

`ncg_scan_maps_for_base_apk()` 用 `strchr(line, '/')` 取路径，遇到 Android 12+ 的
dalvik 匿名映射行（`[anon:dalvik-classes.dex extracte...=/com.x.base.A==/base.apk]`）
会取出缺前缀带尾括号的假路径 → `open` 失败 → k_so 派生 -12 → 不解密 → SIGBUS。
**只在包内多个 dex 被 dalvik 映射时触发**。修法：抽出 `ncg_path_from_maps_line()`，
四条判据（`/` 开头 / `base.apk` 结尾 / 不含 `[]` / open 成功）；不能拒绝 `=`
（安装目录名常含 base64 风格 `==`，合法）。回归：V0（8 用例）。

#### ② 补发混淆（本次 tag 的真正目的）

原 `v0.9.48-maps-fix` 修复版**没有推 tag**，是本地直接 `make-zip-lib.sh` 打的——
未设 `AMICE_BUNDLE` → **普通编译，nox 层 VMP/MBA 静默全部丢失**，且：

- 消费方 `test-so-lock.sh` 全套 52 项用 `ensure_nox_src` **源码**编译，不消费 .a
  → "换了没混淆的 .a" 在全部测试里照绿；
- 消费方工具包版本表的描述字段从 v0.9.47-obf 复用（"两套 VMP 均生效"），未实测核对
  → 文档也声称有。

两个月后由 artifact-pipeline 侧以"so 只有 88.66K"的用户直觉质疑揭穿
（实测 `ncg_xor_key` 16 条指令，VMP 形态应 ~210；产物无 `.ncr/.ncq/.ncs/.nct/.ncv/.ncw`）。

**教训（两侧文档均已同步）**：Amice 混淆只能烧死在 nox 打包期（.a 是已编译机器码，
消费方无法事后补）——生产分发**必须**走 `-obf` 通道；本地直打必须设
`AMICE_BUNDLE`；消费方已有产物侧断言（`test-so-lock.sh` T34）拦无混淆包。

**诚实记录**：本次事故中 V15 自检（版本文档 == git tag）也拦了一次——
v0.9.48-maps-fix 打包时连 tag 都没推（V15 检测不到），本 tag 首推时被 V15
以"文档=v0.9.47 tag=v0.9.48"拦下，遂先补本文档再重打 tag。V15 只能拦
"打了 tag 不改文档"，拦不住"根本不打 tag"——消费方 T34 补上了这半边。

### v0.9.47-noreport-obf（2026-11-19）当前版

**调试报告改为编译期开关** —— 修 0 信息逆向报告标 ★★★ 的两个弱点。

#### 问题（外部 0 信息逆向实测，2026-11-18）

逆向者用 Unicorn 仿真执行 `init_array`、hook `getenv`/`access`，
**5 秒**就找到两个调试开关：

```
[imp] getenv   'NCG_REPORT_PATH'
[imp] access   '/storage/emulated/0/xixin_debug' → -1
```

而这两个字符串在 `.rodata` 是**明文** —— `strings libnc.so | grep xixin`
一条命令就能看到，**不需要任何逆向技能**。看到之后 `touch` 一下，
壳就把 12 步解密流水线写成中文报告：

```
U1 resolve_self 进入 → OK so_path
U2 找 .ncx 段 → OK .ncx 大小
...
U9 boot_key 派生 → OK
U12 派生 k_so（读证书+包名）
```

等于把「逆向 12 个未知函数」降级成「读一份自述文档」。

#### 为什么不能只改名

用户明确反对（原文：「改文件名那我以后怎么调试」）。名字必须可读，
否则自己也记不住。

#### 为什么不用 Android 的 debuggable

`protect.sh` 已强制 `debuggable=false` —— 那是安全要求（debuggable=true
会让 `run-as` 进沙箱、调试器 attach，绕过反调试）。不能为调试改回去。

#### 改法

`nc_guard_report.c` 的 `ncg_debug_log_path()` 整体包进 `#ifdef NCGUARD_DEBUG_REPORT`：

- **release 构建不定义该宏** → 这段代码根本不存在，
  `strings` 搜不到 `xixin_debug`，也搜不到 `getenv` 调用
- **要调试时**构建期加 `-DNCGUARD_DEBUG_REPORT`

#### 怎么出调试包

```bash
# 平时构建（默认，无报告代码）
python3 scripts/trigger_build.py app.apk --sigcheck --vmp

# 调试构建（带自检报告）
DEBUG_REPORT=1 python3 scripts/trigger_build.py app.apk --sigcheck --vmp
```

报告路径不变：`/storage/emulated/0/Android/data/<包名>/files/ncguard_log.md`

> ⚠️ 调试包**不能发给用户** —— 它有调试开关。
> 但它的强度与正式包相同（只多一个报告模块），可用于真机排障。

#### 改的文件

- `scripts/so-guard/nc_guard_report.c`：`ncg_debug_log_path()` 加 `#ifdef`

#### 验证

- release 模式（不定义宏）编译通过
- 调试模式（`-DNCGUARD_DEBUG_REPORT`）编译通过
- **未验证**：`strings` 在 release 产物里确实搜不到 —— 需打完包实测

### v0.9.46-alltext-enc-obf（2026-11-14）当前版

**只有自检报告的可读性改动，防护行为零变化。**

## 版本号命名约定

```
v0.9.<序号>-<标签>
```

**标签含义**（尽量用能说明改动的词）：

| 标签 | 含义 |
|---|---|
| `-plain` | 段不加密（明文优先，体积小） |
| `-obf` | 含 Amice 混淆（MBA + flatten） |
| `-vmp` | 含 VMP 虚拟化 |
| `-nct` / `-insn` / `-bc` / `-seg` | 该轮实验的段相关改动 |
| `-log` | 日志/报告相关 |

**⚠️ 标签不得暴露防护意图**（流程文档的通用纪律）。但版本标签留在这里是为
人类维护者服务的，不出现在产物里（产物只有 `VERSION` 文件一行版本号）。
