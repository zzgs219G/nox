# 版本记录

> **本文件是 nox 的版本真相表。** 与 `git tag` 两条线都要维护：
> - `git tag` = 可复现的代码快照
> - 本表 = 人能读的版本说明
>
> ⚠️ **换版时必须同时做三件事**：打 tag、更新本表、更新消费方的
> `artifact-pipeline/tools/工具包版本.md`。曾因漏更新消费方那行，
> 版本表落后 25 个版本（11-13 实测发现）。
>
> 核对方法：
> ```bash
> git describe --tags           # 仓库当前 tag
> unzip -p ../artifact-pipeline/tools/nox.zip nox/VERSION   # 消费方实际用的
> ```
> 两者必须一致。

### v0.9.50-logfix-obf（2026-11-24）当前版

grep，靠真机终验钉住。

### v0.9.48-maps-fix-obf（2026-11-24）

两件事打包成一个 tag：

#### ① maps 路径解析修复（原 v0.9.48-maps-fix 的内容，commit 00dbb50）

`ncg_scan_maps_for_base_apk()` 用 `strchr(line, '/')` 取路径，遇到 Android 12+ 的
dalvik 匿名映射行（`[anon:dalvik-classes.dex extracte...=/com.x.base.A==/base.apk]`）
会取出缺前缀带尾括号的假路径 → `open` 失败 → k_so 派生 -12 → 不解密 → SIGBUS。
**只在包内多个 dex 被 dalvik 映射时触发**。修法：抽出 `ncg_path_from_maps_line()`，
四条判据（`/` 开头 / `base.apk` 结尾 / 不含 `[]` / open 成功）；不能拒绝 `=`
（安装目录名常含 base64 风格 `==`，合法）。回归：V0（8 用例）。

#### ② 补发混淆（本次 tag 的真正目的）

原 `v0.9.48-maps-fix` 修复版**没有推 tag**，是本地直接 `make-zip-lib.sh` 打的——
未设 `AMICE_BUNDLE` → **普通编译，nox 层 VMP/MBA 静默全部丢失**，且：

- 消费方 `test-so-lock.sh` 全套 52 项用 `ensure_nox_src` **源码**编译，不消费 .a
  → "换了没混淆的 .a" 在全部测试里照绿；
- 消费方工具包版本表的描述字段从 v0.9.47-obf 复用（"两套 VMP 均生效"），未实测核对
  → 文档也声称有。

两个月后由 artifact-pipeline 侧以"so 只有 88.66K"的用户直觉质疑揭穿
（实测 `ncg_xor_key` 16 条指令，VMP 形态应 ~210；产物无 `.ncr/.ncq/.ncs/.nct/.ncv/.ncw`）。

**教训（两侧文档均已同步）**：Amice 混淆只能烧死在 nox 打包期（.a 是已编译机器码，
消费方无法事后补）——生产分发**必须**走 `-obf` 通道；本地直打必须设
`AMICE_BUNDLE`；消费方已有产物侧断言（`test-so-lock.sh` T34）拦无混淆包。

**诚实记录**：本次事故中 V15 自检（版本文档 == git tag）也拦了一次——
v0.9.48-maps-fix 打包时连 tag 都没推（V15 检测不到），本 tag 首推时被 V15
以"文档=v0.9.47 tag=v0.9.48"拦下，遂先补本文档再重打 tag。V15 只能拦
"打了 tag 不改文档"，拦不住"根本不打 tag"——消费方 T34 补上了这半边。

### v0.9.47-noreport-obf（2026-11-19）当前版

**调试报告改为编译期开关** —— 修 0 信息逆向报告标 ★★★ 的两个弱点。

#### 问题（外部 0 信息逆向实测，2026-11-18）

逆向者用 Unicorn 仿真执行 `init_array`、hook `getenv`/`access`，
**5 秒**就找到两个调试开关：

```
[imp] getenv   'NCG_REPORT_PATH'
[imp] access   '/storage/emulated/0/xixin_debug' → -1
```

而这两个字符串在 `.rodata` 是**明文** —— `strings libnc.so | grep xixin`
一条命令就能看到，**不需要任何逆向技能**。看到之后 `touch` 一下，
壳就把 12 步解密流水线写成中文报告：

```
U1 resolve_self 进入 → OK so_path
U2 找 .ncx 段 → OK .ncx 大小
...
U9 boot_key 派生 → OK
U12 派生 k_so（读证书+包名）
```

等于把「逆向 12 个未知函数」降级成「读一份自述文档」。

#### 为什么不能只改名

用户明确反对（原文：「改文件名那我以后怎么调试」）。名字必须可读，
否则自己也记不住。

#### 为什么不用 Android 的 debuggable

`protect.sh` 已强制 `debuggable=false` —— 那是安全要求（debuggable=true
会让 `run-as` 进沙箱、调试器 attach，绕过反调试）。不能为调试改回去。

#### 改法

`nc_guard_report.c` 的 `ncg_debug_log_path()` 整体包进 `#ifdef NCGUARD_DEBUG_REPORT`：

- **release 构建不定义该宏** → 这段代码根本不存在，
  `strings` 搜不到 `xixin_debug`，也搜不到 `getenv` 调用
- **要调试时**构建期加 `-DNCGUARD_DEBUG_REPORT`

#### 怎么出调试包

```bash
# 平时构建（默认，无报告代码）
python3 scripts/trigger_build.py app.apk --sigcheck --vmp

# 调试构建（带自检报告）
DEBUG_REPORT=1 python3 scripts/trigger_build.py app.apk --sigcheck --vmp
```

报告路径不变：`/storage/emulated/0/Android/data/<包名>/files/ncguard_log.md`

> ⚠️ 调试包**不能发给用户** —— 它有调试开关。
> 但它的强度与正式包相同（只多一个报告模块），可用于真机排障。

#### 改的文件

- `scripts/so-guard/nc_guard_report.c`：`ncg_debug_log_path()` 加 `#ifdef`

#### 验证

- release 模式（不定义宏）编译通过
- 调试模式（`-DNCGUARD_DEBUG_REPORT`）编译通过
- **未验证**：`strings` 在 release 产物里确实搜不到 —— 需打完包实测

### v0.9.46-alltext-enc-obf（2026-11-14）当前版

**只有自检报告的可读性改动，防护行为零变化。**

① 段表表头与数据行对齐（用户反馈「文本歪歪扭扭」）
   · 表头原是三行手写字面量，与数据行的 `%9llu / %-4s / %6.3f` 格式串
     毫无关系 → 逐列错位。实测表头 `[0,10,18,25,31,53]`、
     数据行 `[0,13,21,27,34,52]`。
   · 改为按实测列位写死的字面量，注释写明「改 rp_seg 格式串必须重算」。
   · 试过用 rp_pad 逐列补绝对列位，失败：rp_pad 语义是「补到总宽至少
     N 显示列」，不是「补到列 N」，会算出 20+ 空格。

② 判定前缀宽度统一为 2 字符
   · `! 样本不足`（1空格）与 `!  高熵未解密`（2空格）宽度不一
   · fallback 的 `明文`/`密文` 无前缀 → 补 3 空格与 `OK `/`XX ` 等宽

③ 体积归因（上一提交 8cf109e 已含）
   · 按 nox设施 / VMP载荷 / 业务载荷 / 基础代码 四组汇总 + 组内明细
   · 整组不存在也打 0 B（区分「没开 VMP」与「统计漏了」）

**断言**：V12g（四组齐全）/ V12h（有合计行）/ V12i（表头与数据行列位一致）。
V12i 不比较大小和熵 —— 它们右对齐，起始列随数字位数变化，比起点会误报。
nox test.sh 44 通过 0 失败。

**产物体积**（arm64，含 dex2c + sigcheck + 两套 VMP）：
```
libnc.so        813,616 B
APK（zlib 后） 5,454,411 B
```

**VMP 生效判据**（实测，非推断）：
```
.text 里 bl→.ncr = 13 处   第一套（nox 解密链，14 个函数）
.nc x 里 bl→.nct =  9 处   第二套（sig_check 的 11 个减去 2 个被 skip 的）
```

### v0.9.26 ~ v0.9.28（2026-11-12）

`.nct` 段进锁箱的三次尝试，全部失败：

| 版本 | 改动 | 结果 |
|---|---|---|
| v0.9.26-nct-obf | `.nct` 段进锁箱 | ❌ SIGILL |
| v0.9.27-nct-obf | 段序改动态 + 修正段名抽取正则（`NC_SEC_VMP2` 带数字） | ❌ 仍崩 |
| v0.9.28-nct-plain | `.nct` 不参与解密 | 回滚 |

**当时的判断（后来证伪）**：以为是"段名导致崩溃"。
**真因**（11-13 查明）：`.ncr` 里有 83 个 `R_AARCH64_RELATIVE` 重定位，
整段加密后解锁写回会覆盖链接器填的指针 → 垃圾指针 → SIGILL。
**与段名无关**，与"是否含指针"有关。

### v0.9.11-obf（2026-11-11）

**关闭解密链 VMP**（`v0.9.11-novmp`）。理由见 `so防护架构.md` §14：

**该决定后来被推翻**（11-12 恢复），但核心结论仍成立：
"要结果 → VMP 无效；要逻辑 → VMP 有效"。

### v0.9.0 ~ v0.9.10（2026-11-06 ~ 11-09）

（函数级隔离，逆通一个只能读一个）。

## 版本号命名约定

```
v0.9.<序号>-<标签>
```

**标签含义**（尽量用能说明改动的词）：

| 标签 | 含义 |
|---|---|
| `-plain` | 段不加密（明文优先，体积小） |
| `-obf` | 含 Amice 混淆（MBA + flatten） |
| `-vmp` | 含 VMP 虚拟化 |
| `-nct` / `-insn` / `-bc` / `-seg` | 该轮实验的段相关改动 |
| `-log` | 日志/报告相关 |

**⚠️ 标签不得暴露防护意图**（流程文档的通用纪律）。但版本标签留在这里是为

## 待办：历史 tag 与版本号的对应

**v0.9.30 ~ v0.9.36 只构建过、从未打 tag**（当时是用
`gh workflow run -f version=...` 临时指定版本号）。这些版本的具体内容
散落在构建记录里，**不可复现**，不建议补 tag。

若要复现某次构建，用 `git log` 按时间的提交找，然后重新构建。

**教训**：每次发版必须打 tag。否则"这个包是哪份代码编的"无从查起。
