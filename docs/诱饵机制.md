# 诱饵组（bait groups）— 设计说明与维护须知

> **最后更新：2026-11-27**
> 这份文档只讲一件事：`nc_guard_decoy.c` + `so-section-lock.py --bait` 这套
> 诱饵机制**为什么这么写**、**哪些地方一改就废**。

---

## 0. 三十秒理解

产物里现在有 **N+1 组**结构完全相同的加密段：

```
.ncx    .ncxh    .ncks    .ncxhr      ← 真的（程序用这一组）
.ncx0   .ncxh0   .ncks0   .ncxhr0     ← 诱饵
.ncx1   .ncxh1   .ncks1   .ncxhr1     ← 诱饵
```

它们在**段表上无法区分**：权限、大小、命名风格逐项相同。

攻击者必须**逐组跑完整条派生链**，直到最后一步（用解出的 master 派生
`k_so` 去解 `.ncx`）才能判断真假。单组成本 ≈ 真链成本。

---

## 1. 诱饵必须满足的四条（缺一条就废）

这是全部设计的核心。**任何一条被破坏，诱饵自动失效，而且失效是静默的**
—— 产物照样能跑、功能正常，只是防护归零。所以每一条都在 `test.sh` 的
**V18** 里有断言。

### ① 槽的 HMAC 必须自洽

攻击者拿到任一组的第一件事是验 `expect_mac_head`：

```
k_mac_head = 槽[48:64] ^ XOR_KEY
HMAC-SHA256(k_mac_head, head密文) == 槽[64:96] ?
```

**必须让他验过。** 若验不过，他第一步就排除这组 —— 诱饵等于没做。

`bait_groups()` 里这行是关键：

```python
expect_mac_g = hmac_sha256(k_mac_g, head_cipher)   # 用【诱饵自己的】k_mac_g
```

若误写成 `b'\x00'*32` 或随机值，V18c 立刻红。

### ② head 明文必须是真实 ARM64 代码

攻击者验证「解开没有」的标准动作是反汇编前几条指令。

**必须让他看到合法的函数序言**（`sub sp,sp,#N` / `stp x29,x30,[sp,#-N]!`）。
若诱饵明文是随机字节，反汇编得到一堆非法指令 → 立刻排除。

`_pick_code_region()` 负责这件事：它**只在真实函数序言签名处取样**。
实测踩过的坑（2026-11-27）：早先版本随便从 `.text` 中段取，结果落在
字面量池，解出来是 `0x0b0d016b` 这类非法指令，诱饵被一眼识破。

### ③ 诱饵 `.ncx` 必须能用【真证书 + 真包名】解开

攻击者会用 APK 里的真证书派生 `k_so`：

```
k_so = HKDF(master_g, SHA256(certDER), "nc-so-v1" + 包名)
```

若诱饵 `.ncx` 用别的证书加密，他解得乱码 → 排除这组。

所以 `nox protect` 调用 `--lock-head` 时**必须传 `--from-apk`**：

```python
run([sys.executable, lock_py, step1, step2, '--lock-head',
     '--from-apk', os.path.abspath(args.apk)] + ...)
```

漏了这个参数，诱饵 `.ncx` 只能用全零证书，攻击者一解就露馅。

### ④ 诱饵段必须与真段【同尺寸同权限】

这是最容易忽略、也最好识破的一条。

实测踩过（2026-11-27 第一版）：真 `.ncx` 192B，诱饵 `.ncx0` 8196B ——
差 42 倍。攻击者 `readelf -S | sort -k6` 一条命令就认出真段。

所以 `bait_groups()` 里有一段**尺寸对齐**：

```python
_resize_section(elf, head, target_head)   # 改 sh_size，不挪数据
_resize_section(elf, code, target_code)
_resize_section(elf, ro,   target_ro)
```

⚠️ **只能缩小不能放大**（放大要挪数据、改后续所有 `sh_offset`，会破坏
已有的段地址）。所以 `nc_guard_decoy.c` 里的声明尺寸必须**大于等于**
真段可能达到的最大尺寸 —— 见该文件 `NCG_BAIT_HEAD_PAD` / `NCG_BAIT_CODE_MAX`
的注释。实测 v7a 的真 `.ncxh` 比 arm64 大 400B，所以留了 8KB 余量。

## 2. 段名随机化（2026-11-28）

**问题**：改前段表是 `.ncx` / `.ncx0` / `.ncx1` —— 任何逆向者 2 秒就知道
「没数字后缀的是原件」。这是段表白送的答案，比大小、比 MAC 都更直接。

**做法**：真段名动不了（解锁链 `ncg_find_section` 按名字查），但**诱饵不被
任何代码引用，叫什么都可以**。锁箱时把诱饵名改成随机：

```
改前: .ncx   .ncx0   .ncx1      .ncxh   .ncxh0   .ncxh1
改后: .ncx   .ymq    .hoq       .ncxh   .j9ch    .o7uv
```

**三条生成规则**（都是实测段表后修出来的，早期版本违反过）：

| 规则 | 违反后的样子 | 为什么假 |
|---|---|---|
| 不能叫 `.decoy0`/`.bait0` | `.bait0` | 等于写「我是假的」 |
| 首字符必须是字母 | `.1ln` | 真实段名无一例外（`.text`/`.bss`/`.got`/`.plt`） |
| 长度与对应真段相同 | `.1ln`(4) 与 `.rerq`(5) 混排 | 长短参差比原方案更可疑 |

**实现：原地改 shstrtab 字符串，不用 objcopy。**

`AGENTS.md §5.4` 警告 objcopy 重写 ELF 会挪 `sh_addr` → 运行期基址计算
全错，且崩溃点是 `.ncxh` 里的 SIGILL（症状完全不指向 objcopy）。
实测本方案段地址完全不变（`0x630` → `0x630`）。

⚠️ 约束：新名长度必须 ≤ 原名长度（段名在 shstrtab 里是紧凑 NUL 串，
写超长会覆盖下一个段名）。

⚠️ **段名随机化后，所有按 `.ncxh0` 找诱饵的代码都会失效**。
`test.sh` 的 V18b/V18c 已改为按【段属性 + 尺寸】识别（`SHF_EXECINSTR`
且与真段同量级）。任何新增的诱饵相关断言都必须用属性判定，不能依赖名字。

## 2.1 五个「一改就废」的地方

| 位置 | 改错了会怎样 |
|---|---|
| `nc_guard_decoy.c` 的段名（`.ncxh0` 等） | 必须与 `_bait_specs()` **逐字一致**，否则段找不到 → 锁箱失败。**注意：这是链接期的名字，锁箱后会被随机化改写**，两者不是一回事 |
| 诱饵 head 用**函数 + `.space`**，不是数组 | 数组是 `AR`，真段是 `AXR`。属性不同 = 段表直接标「这是假的」 |
| 诱饵 master 用 `volatile`，不是 `const` | 真 `.ncxhr` 是 `WAR`（运行期要 mprotect 成 RW）。`const` 会变 `AR` |
| `bait_groups` 必须在 `_encrypt_slots()` **之后** | 否则诱饵槽被 T4 加密，但诱饵链派生规则里没有这一步 → 攻击者解不出 → 露馅 |
| 诱饵槽自己也要过 **T4**（boot_key RC4） | 见 `bait_groups` 里 `boot_key_g = _derive_boot_key(elf)` 那段。漏了攻击者解密拿到乱码 |

## 3. 真路径零污染（可维护性）

**这是刻意的约束：诱饵不能让我们自己维护时也被绕晕。**

- `nc_guard_boot.c`（解锁链主体）**一行没动**。诱饵对运行期零影响。
- 诱饵全部代码在两个地方：
  - `scripts/so-guard/nc_guard_decoy.c`（只声明占位段，零逻辑）
  - `so-section-lock.py` 的 `bait_groups()`（只在 `lock_head` 尾部被调用一次）
- 真链完全不引用诱饵符号 —— `--gc-sections` 靠 `used`/`retain` 保住它们。

**排查产物的正确顺序**：先看 `readelf -SW | grep ncx`，若出现 `.ncx0`
说明诱饵生效。若想临时关掉：`NCG_BAIT_N=0` 重新编译（产物里零诱饵段）。

## 4. 组数怎么调

```c
// nc_guard_decoy.c
#ifndef NCG_BAIT_N
#  define NCG_BAIT_N 2      // ← 改这里
#endif
```

| 组数 | 产物增量 | 攻击者成本 |
|---|---|---|
| 0 | 0 | 直接命中真链（无干扰） |
| 2（默认） | ≈ +8.8KB | 需排除 2 组，成本 ×3 |
| 4 | ≈ +17.6KB | 需排除 4 组，成本 ×5 |

⚠️ 加组数要同时在 `nc_guard_decoy.c` 里补 `#if NCG_BAIT_N >= 5` 分支，
否则编译期 `_Static_assert` 会拦（防「以为加了其实没加」的静默失败）。

## 5. 这套东西的边界（如实）

**它不是加密，是提高成本。**

- 攻击者若**运行**产物并 hook `.ncx` 的执行，能立刻定位真段
  —— 诱饵对动态分析无效，只对静态分析有效。
- 攻击者若能读源码（仓库公开），能直接看出 `bait_groups` 的存在
  —— 但那需要先知道有这个机制。产物里没有任何字符串指向它。
- **真正的解法仍是根密钥移出产物**（服务端/Keystore/许可证）。
  诱饵是在那之前能把静态成本抬高一个量级的过渡手段。

判据（照 `AGENTS.md §3.5`）：**一个防护如果最终是一个 `if`，它就能被
patch。** 诱饵不改变密码学结论，它只是让攻击者在错误的路径上多花时间。

### 5.1 一条修不了的硬限制（2026-11-28 补充）

段名随机化解决了「无后缀 = 原件」，但**没有解决**这一条：

```
.text 里硬编码真段地址 —— 反汇编 ncg_head_unlock 就能读到
    ncg_find_section(so_path, ".ncx", &sec)   // 名字写死在明文里
```

一个会用 `objdump -d` 的攻击者，5 分钟就能定位真段，诱饵全部失效。

要修必须把解锁链改成「遍历所有候选段 + 逐个试解密 + 验 MAC」。代价：
改 `ncg_head_unlock` 核心流程、破坏 `AGENTS.md §1.2` 的段名契约、
**崩溃症状是 SIGILL（App 起不来），只能真机验证**。

**所以当前诱饵的真实定位是**：挡住「只看段表就下结论」的自动化工具和
快速判断，挡不住反汇编 `.text` 的定向分析。不要高估。
