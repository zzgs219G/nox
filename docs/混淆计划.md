## 2. P0：藏三个泄露锚点（最划算）

现状是**"读懂"贵了但"认出"没贵**。三个锚点：

### 2.1 HKDF label 明文（`nc-boot-v1` / `nc-so-v1` / `nc-so-mac-v1`）

```
位置：.rodata，strings 直接可见
作用：xref 一下就定位到 ncg_boot_key
```

**难点**：`NC_BOOT_INFO` 在 `nc_guard_layout.h`（冻结契约），且
`so-section-lock.py` 用正则从这个 `#define` 抽取（C 与 Python 必须同源）。

**做法**（三选一，按侵入性递增）：
```
① 把 label 拆成两段，运行期拼接
     #define NC_BOOT_INFO_A "nc-bo"
     #define NC_BOOT_INFO_B "ot-v1"
     → Python 侧也要改成拼接，且保证结果逐字节一致
② 运行期从 slot 里读（利用已有的 XOR_KEY）
     → 但 slot 在解锁前是密文，会引入循环依赖 ← 不可行
③ 接受现状，只做下面两条
```

⚠️ **改 `nc_guard_layout.h` = 破坏所有历史产物**。改之前先跑
`test-so-lock.sh` 的 T20/T22，并确认消费方会跟上换版。

### 2.2 HKDF 参数明文（`mov w1,#0x24` / `mov w3,#0x10` / `mov w5,#0xa`）

```
位置：ncg_boot_key 函数体
原因：函数调用参数走 ABI，混淆器改不了
```

**做法**：让长度在运行期算出来，编译器不知道是常量。

```c
/* 现在 */
khkdf_sha256(ikm, 36, salt, 16, (const uint8_t*)NC_BOOT_INFO, 10, out, 16);

/* 改成 */
volatile size_t ikm_len = sizeof(ikm);              /* sizeof 会被折叠，加 volatile 打断 */
size_t info_len = strlen(NC_BOOT_INFO);             /* 运行期算 */
khkdf_sha256(ikm, ikm_len, salt, sizeof(salt), ...);
```

⚠️ **必须验证**：`-Oz` 下 `volatile` 能否真的阻止常量折叠。改完反汇编
确认 `mov w1, #0x24` 消失（变成 `ldr` 或运行期计算）。

### 2.3 FLA 状态码明文（`mov w8,#0x8937`）

```
位置：被混淆函数开头，集中列出
原因：flatten_mode=basic 不清洗状态码
```

**做法**：先试 P3（换 `dominator` 模式），一行改动。

## 3. P1：`ncg_boot_key` 拆文件 + VMP

### 3.1 要搬的依赖

```
ncg_boot_key 依赖：
  ncg_boot_crc32      (8 行)   ← 一起搬
  ncg_elf_hdr         (34 行)  ← 一起搬
  ncg_elf_shdr        (23 行)  ← 一起搬
  ncg_stub_find_text  (39 行)  ← 一起搬
  ncg_slot_read       (50 行)  ← 一起搬（它只依赖 ncg_boot_key + ncg_stub_slot + ncg_magic_ok）
  ncg_wipe            (35 处引用) ← 不能搬，保留在 boot.c 改外部符号
  khkdf_sha256        (nc_guard_key.c) ← 已是外部
```

### 3.2 关键阻塞点（必须先验证）

`ncg_slot_read` 靠 `&ncg_stub_slot` 的 PC 相对地址反推镜像基址：

```c
uintptr_t img_base = (uintptr_t)&ncg_stub_slot - stub_sh_addr;
```

`ncg_stub_slot` 现在是：

```c
__attribute__((section(NC_SEC_STUBSLOT), used, aligned(1), retain))
static const volatile unsigned char ncg_stub_slot[NC_STUB_SIZE] = {0};
```

**从 `static` 改成外部符号后，跨 TU 引用可能变成 GOT 间接寻址**，
`&ncg_stub_slot` 拿到的值会不同 → 基址反推错 → 解锁链全崩。

#### 验证步骤（做 P1 之前必须走完）

```bash
# ① 只把 ncg_stub_slot 改外部，其他一律不动
#    boot.c:  static const volatile ... → const volatile ...（去 static）
#    boot.c:  加 extern 声明（供新文件用）

# ② 编译 + 检查段属性是否保住
readelf -SW libnc.so | grep ncks
#   期望：size = 0x70 (112)，flags 含 A/R

# ③ 检查符号是否泄漏到 .dynsym
readelf --dyn-syms libnc.so | grep -c ncg_stub_slot
#   期望：0（-fvisibility=hidden 应拦住）

# ④ 锁箱三步，检查 .ncks 段还在
python3 so-section-lock.py ... --section .ncx --from-apk <apk>
python3 so-section-lock.py ... --lock-head
readelf -SW libnc.so | grep -E 'ncks|nck|ncxh'
#   期望：三个都在，且 .ncks size 仍 0x70

# ⑤ 真机 selftest==59
#   这一步不能省 —— 基址反推错的表现就是 selftest != 59 或崩溃
```

**如果 ④/⑤ 失败** → 说明 GOT 间接寻址破坏了基址反推。退路：

```
退路 A：让 ncg_slot_read 留在 boot.c，只搬 ncg_boot_key
        （但 ncg_slot_read 调用 ncg_boot_key，会变成反向依赖 → 需重新设计）
退路 B：放弃 ncg_boot_key 的 VMP，只保留 MBA+FLA
```

### 3.3 拆完的验证

```bash
# VMP 是否生效（关键判据，别只看体积）
ar x libnox.a && llvm-objdump -d --disassemble-symbols=ncg_boot_key nc_guard_boot.o | grep -c ':'
#   期望：数百条（含 movk lsl #48 / sub sp,sp,#0xc0）
#   若十几条 → 被跳过，查 RUST_LOG=amice=debug
#
# ⚠️ 目标文件名是 nc_guard_boot.o（不是 nc_guard_crypto.o —— 没有那个
#    文件）。拆出新 .c 之后目标文件名随之改变，用 `ar t libnox.a` 先确认。
```

## 4. P2：`ncg_stub_recover` 拆文件 + VMP（风险最高）

### 4.1 为什么风险高

```
· 138 行（最大的一个）
· 依赖 7 个函数 + dladdr + mprotect + khmac_sha256
· 在 constructor(50) 关键路径上，是解锁链第一环
· 有时序约束：先验 MAC 再 mprotect 再解密；用后即毁
```

VMP 引入的额外栈操作（`sub sp, sp, #0xc0`）和函数调用可能影响它
假设的栈布局。但**时序逻辑本身（先验后解）不受影响** —— 已确认过。

### 4.2 前置条件

**必须先完成 P1 并真机验证通过。** 理由：`ncg_stub_recover` 依赖
`ncg_slot_read`，而 `ncg_slot_read` 的搬迁风险在 P1 里已经验过。
P1 不通，P2 一定不通。

### 4.3 拆法

```
新建 nc_guard_crypto.c：
  ncg_stub_recover
  ncg_ctr_xor        (17 行)
  + P1 搬过来的那些
```

文件级 `AMICE_VM_VIRTUALIZE=true`（与 `nc_guard_xor.c` 同样的手法）。

⚠️ 注意：**不能给整个文件开 VMP 后还保留 annotate**（互斥，见
`流程文档.md` 4.3.4）。所以 P1/P2 搬进 `nc_guard_crypto.c` 的函数
要全部去掉 `NC_OBF`。

### 4.4 崩了怎么排查

VMP 后的崩溃极难查（pc 落在解释器里，看不出是哪个函数）。排查顺序：

```
① 先确认是 VMP 的问题还是别的：把 AMICE_VM_VIRTUALIZE 去掉重编
   → 若是 VMP 的问题，不虚拟化就正常
② 缩小范围：只虚拟化 ncg_ctr_xor（最小的），确认 VM 机制本身没问题
③ 查 VM 帧：ncg_stub_recover 里有大栈数组吗？（mprotect 段计算用）
   VMP 解释器自己也要栈，加起来可能超默认线程栈
④ 实在不行：降级成 MBA+FLA（P1 的 NC_OBF 组合）
```

## 5. P3：`flatten_mode=dominator`（一行改动，先试）

```
现在：annotate("+flatten")              → 默认 basic 模式，状态码明文
改成：annotate("+flatten,flatten_mode=dominator")
```

Amice 文档称 dominator 是"支配树加强版，可配合总是内联策略强化混淆"。

**判据**：改完反汇编看状态码是否还是明文常量集中出现。

```bash
llvm-objdump -d --disassemble-symbols=ncg_boot_key nc_guard_boot.o \
  | grep -E 'mov\s+w[0-9]+, #0x[0-9a-f]{4}' | head
#   basic 模式：函数开头一堆 mov wN,#0x????（状态码）
#   dominator：若被加密，这些常量应消失或变化
```

⚠️ 体积会涨，且可能在 `constructor(50)` 上引入新的边界风险。
改完必须真机验 `selftest==59`。

## 7. 不建议做的事（及理由）

| 不做 | 理由 |
|---|---|
| **对 `.ncx` 里的业务代码上混淆** | 那是破壳后才可见的代码。混淆它不影响"破壳"这一步，白增体积（实测过：全局开混淆让 `.text` 涨 92%，全来自 dex2c 产物） |
| **VMP 整个文件** | `AMICE_VM_VIRTUALIZE` 是文件级开关。对整个 `nc_guard_boot.c` 开会虚拟化 25+ 个函数，体积 +300~500% |
| **自编译 OLLVM** | stock NDK clang 不认识 `-mllvm -fla`，要自建整套工具链。Amice 是插件，零成本达到同样目的 |
| **换 RC4** | 已论证：软件 AES 比软件 RC4 慢 2.6×，v7a 无硬件 AES；RC4 在本场景（一次性加密、高熵明文、无密钥复用）不满足任何已知攻击前提 |
| **改 6 个段名** | 要动契约头 + 26 处字面量 + 全部测试，收益只是"降低可发现性"；熵值扫描照样能定位 |
