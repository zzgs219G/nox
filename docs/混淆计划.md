### 0.2 `.ncx` 不是 VMP 段

新手最容易搞错的一点：

```
.nc x  业务代码的加密段（39 KB，加密）
       里面有：10 个 dex2c 业务方法（明文 ARM64）
```

`.ncx` 里只有壳，逻辑在 `.ncv`（第二套）或 `.ncq`（第一套）。

### 关于瘦身（用户口径：先防御后瘦身，现在防御做完了）

`scope=func` 让 14 个函数各有一套 VM 运行时，体积 245 KB → 406 KB。
但**它们共用同一份 `isa.vm`**（2246 行），攻击者逆出一套 VM 语义后，
其他几套只是"换个 opcode 编码表"，边际成本远低于 ×11。

回退办法：

```bash
AMICE_VMP_PROFILE=simple ./scripts/make-zip-lib.sh <ver>-obf
# 用内置 amice-simple-vmp（module 共享），省约一半体积
```

⚠️ 回退前先确认真机验证通过了 `scope=func` 版本 —— 否则分不清
"体积变小"和"强度变化"哪个是原因。

## 2.1 旧 P0 记录（保留作参考）


现状是**"读懂"贵了但"认出"没贵**。三个锚点：

### 2.1 HKDF label 明文（`nc-boot-v1` / `nc-so-v1` / `nc-so-mac-v1`）

```
位置：.rodata，strings 直接可见
作用：xref 一下就定位到 ncg_boot_key
```

**难点**：`NC_BOOT_INFO` 在 `nc_guard_layout.h`（冻结契约），且
`so-section-lock.py` 用正则从这个 `#define` 抽取（C 与 Python 必须同源）。

**做法**（三选一，按侵入性递增）：
```
① 把 label 拆成两段，运行期拼接
     #define NC_BOOT_INFO_A "nc-bo"
     #define NC_BOOT_INFO_B "ot-v1"
     → Python 侧也要改成拼接，且保证结果逐字节一致
② 运行期从 slot 里读（利用已有的 XOR_KEY）
     → 但 slot 在解锁前是密文，会引入循环依赖 ← 不可行
③ 接受现状，只做下面两条
```

⚠️ **改 `nc_guard_layout.h` = 破坏所有历史产物**。改之前先跑
`test-so-lock.sh` 的 T20/T22，并确认消费方会跟上换版。

### 2.2 HKDF 参数明文（`mov w1,#0x24` / `mov w3,#0x10` / `mov w5,#0xa`）

```
位置：ncg_boot_key 函数体
原因：函数调用参数走 ABI，混淆器改不了
```

**做法**：让长度在运行期算出来，编译器不知道是常量。

```c
/* 现在 */
khkdf_sha256(ikm, 36, salt, 16, (const uint8_t*)NC_BOOT_INFO, 10, out, 16);

/* 改成 */
volatile size_t ikm_len = sizeof(ikm);              /* sizeof 会被折叠，加 volatile 打断 */
size_t info_len = strlen(NC_BOOT_INFO);             /* 运行期算 */
khkdf_sha256(ikm, ikm_len, salt, sizeof(salt), ...);
```

⚠️ **必须验证**：`-Oz` 下 `volatile` 能否真的阻止常量折叠。改完反汇编
确认 `mov w1, #0x24` 消失（变成 `ldr` 或运行期计算）。

### 2.3 FLA 状态码明文（`mov w8,#0x8937`）

```
位置：被混淆函数开头，集中列出
原因：flatten_mode=basic 不清洗状态码
```

**做法**：先试 P3（换 `dominator` 模式），一行改动。

### 3.1 要搬的依赖

```
ncg_boot_key 依赖：
  ncg_boot_crc32      (8 行)   ← 一起搬
  ncg_elf_hdr         (34 行)  ← 一起搬
  ncg_elf_shdr        (23 行)  ← 一起搬

  ncg_slot_read       (50 行)  ← 一起搬（它只依赖 ncg_boot_key + ncg_stub_slot + ncg_magic_ok）
  ncg_wipe            (35 处引用) ← 不能搬，保留在 boot.c 改外部符号
  khkdf_sha256        (nc_guard_key.c) ← 已是外部
```

### 3.2 关键阻塞点（必须先验证）

`ncg_slot_read` 靠 `&ncg_stub_slot` 的 PC 相对地址反推镜像基址：

```c
uintptr_t img_base = (uintptr_t)&ncg_stub_slot - stub_sh_addr;
```

`ncg_stub_slot` 现在是：

```c
__attribute__((section(NC_SEC_STUBSLOT), used, aligned(1), retain))
static const volatile unsigned char ncg_stub_slot[NC_STUB_SIZE] = {0};
```

**从 `static` 改成外部符号后，跨 TU 引用可能变成 GOT 间接寻址**，
`&ncg_stub_slot` 拿到的值会不同 → 基址反推错 → 解锁链全崩。

#### 验证步骤（做 P1 之前必须走完）

```bash
# ① 只把 ncg_stub_slot 改外部，其他一律不动
#    boot.c:  static const volatile ... → const volatile ...（去 static）
#    boot.c:  加 extern 声明（供新文件用）

# ② 编译 + 检查段属性是否保住
readelf -SW libnc.so | grep ncks
#   期望：size = 0x70 (112)，flags 含 A/R

# ③ 检查符号是否泄漏到 .dynsym
readelf --dyn-syms libnc.so | grep -c ncg_stub_slot
#   期望：0（-fvisibility=hidden 应拦住）

# ④ 锁箱三步，检查 .ncks 段还在
python3 so-section-lock.py ... --section .ncx --from-apk <apk>
python3 so-section-lock.py ... --lock-head
readelf -SW libnc.so | grep -E 'ncks|nck|ncxh'
#   期望：三个都在，且 .ncks size 仍 0x70

# ⑤ 真机 selftest==59
#   这一步不能省 —— 基址反推错的表现就是 selftest != 59 或崩溃
```

**如果 ④/⑤ 失败** → 说明 GOT 间接寻址破坏了基址反推。退路：

```
退路 A：让 ncg_slot_read 留在 boot.c，只搬 ncg_boot_key
        （但 ncg_slot_read 调用 ncg_boot_key，会变成反向依赖 → 需重新设计）
退路 B：放弃 ncg_boot_key 的 VMP，只保留 MBA+FLA
```

## 4. ~~P2：`ncg_stub_recover` 拆文件 + VMP（风险最高）~~ ✅ 已完成（2026-11-06）

> **2026-11-08 校正：本节是历史方案记录，任务已做完。**
> 实测 `ncguard_stub_recover` 20 条指令 + VM 子段。
> 实际拆了**四次**才过 VM 寄存器预算（`ncguard_derive_kstub` /
> `ncguard_head_mac_ok` / `ncguard_head_decrypt` / `ncguard_headro_unlock`），
> 所有拆出的函数必须 `noinline`，否则 `-Oz` 内联回去、拆分失效。

### 4.1 为什么风险高

```
· 138 行（最大的一个）
· 依赖 7 个函数 + dladdr + mprotect + khmac_sha256
· 在 constructor(50) 关键路径上，是解锁链第一环
· 有时序约束：先验 MAC 再 mprotect 再解密；用后即毁
```

VMP 引入的额外栈操作（`sub sp, sp, #0xc0`）和函数调用可能影响它
假设的栈布局。但**时序逻辑本身（先验后解）不受影响** —— 已确认过。

### 4.2 前置条件

**必须先完成 P1 并真机验证通过。** 理由：`ncg_stub_recover` 依赖
`ncg_slot_read`，而 `ncg_slot_read` 的搬迁风险在 P1 里已经验过。
P1 不通，P2 一定不通。

### 4.3 拆法

```
新建 nc_guard_crypto.c：
  ncg_stub_recover
  ncg_ctr_xor        (17 行)
  + P1 搬过来的那些
```

文件级 `AMICE_VM_VIRTUALIZE=true`（与 `nc_guard_xor.c` 同样的手法）。

⚠️ 注意：**不能给整个文件开 VMP 后还保留 annotate**（互斥，见
`流程文档.md` 4.3.4）。所以 P1/P2 搬进 `nc_guard_crypto.c` 的函数
要全部去掉 `NC_OBF`。

### 4.4 崩了怎么排查

VMP 后的崩溃极难查（pc 落在解释器里，看不出是哪个函数）。排查顺序：

```
① 先确认是 VMP 的问题还是别的：把 AMICE_VM_VIRTUALIZE 去掉重编
   → 若是 VMP 的问题，不虚拟化就正常
② 缩小范围：只虚拟化 ncg_ctr_xor（最小的），确认 VM 机制本身没问题
③ 查 VM 帧：ncg_stub_recover 里有大栈数组吗？（mprotect 段计算用）
   VMP 解释器自己也要栈，加起来可能超默认线程栈
④ 实在不行：降级成 MBA+FLA（P1 的 NC_OBF 组合）
```

## 7. 不建议做的事（及理由）

| 不做 | 理由 |
|---|---|
| **对 `.ncx` 里的业务代码上混淆** | 那是破壳后才可见的代码。混淆它不影响"破壳"这一步，白增体积（实测过：全局开混淆让 `.text` 涨 92%，全来自 dex2c 产物） |
| **VMP 整个文件** | `AMICE_VM_VIRTUALIZE` 是文件级开关。对整个 `nc_guard_boot.c` 开会虚拟化 25+ 个函数，体积 +300~500% |
| **自编译 OLLVM** | stock NDK clang 不认识 `-mllvm -fla`，要自建整套工具链。Amice 是插件，零成本达到同样目的 |
| **换 RC4** | 已论证：软件 AES 比软件 RC4 慢 2.6×，v7a 无硬件 AES；RC4 在本场景（一次性加密、高熵明文、无密钥复用）不满足任何已知攻击前提 |
| **改 6 个段名** | 要动契约头 + 26 处字面量 + 全部测试，收益只是"降低可发现性"；熵值扫描照样能定位 |

**这一节是 2026-11-06 用 `docs/so逆向文档/` 的零信息逆向报告 + 自己动手
静态解一遍之后写的。它推翻了本文档之前对 VMP 收益的乐观描述。**

### 10.1 实测：不用动态调试就能解出 k_stub

用 Python 照着 `so-section-lock.py` 重写一遍，全程没运行目标 so：

```
① CRC32(.text)           → 0x9ed7ac3b      ✅ 纯静态
② boot_key = HKDF(...)   → 91fae456...     ✅ 纯静态
③ 解 .ncks → XOR_KEY     → e3df1cc6827932c5  ✅ 纯静态
④ k_stub                 → e81b9d92a35d11a6...  ✅ 纯静态
```

**这四步的输入全部来自**：`.text` 字节（明文）、`.ncks` 密文（文件里）、
`NC_XOR_FRAG_INIT` / `NC_BOOT_SALT_INIT` / `NC_BOOT_INFO`（**源码里公开**）。

### 10.2 VMP 保护的 vs 攻击者用的

```
VMP 保护的（那 14 个函数的【实现】）      攻击者实际走的
  ncg_boot_key 的 VMP 字节码                →   _derive_boot_key()（40 行 Python）
  ncg_xor_key 的 VMP 字节码                 →   NC_XOR_FRAG_INIT 常量
  ncguard_derive_kstub                      →   3 行 XOR
  ncguard_head_decrypt                      →   ctr_xor()
```

**两列算的是同一件事。左边焊死了，右边大敞着。**

### 10.3 结论（如实）

**VMP 抬高了「读懂实现」的成本，抬不高「复现算法」的成本。**

它只在一种场景下有价值：攻击者**只有 `libnc.so`**，既没有 APK、
也没有源码仓库。那时他没别的路，只能逆那 14 个函数。

⚠️ 仓库若公开（`so-section-lock.py` 可下载），VMP 在"解 .ncx"这条
路径上的贡献是 **0** —— 攻击者读 Python 就够了，一次都不用碰 VMP。

### 10.4 真正该做什么（按有效性）

| 方向 | 效果 | 代价 |
|---|---|---|
| **让仓库私有** | VMP 立刻有意义 | 零 |
| **让常量每次构建随机**（salt/label/碎片） | 读了 Python 也复现不了 | 中，要改锁箱器 |
| **服务化**（上传 so，服务器加密返回） | 算法不进客户端 | 大，要改架构 |
| 继续加 VMP 覆盖 | 边际收益低（14 个函数已到顶） | 已到极限 |

**别再往 VMP 上加东西了。** 到 14 个函数已经把"容易的"做完，剩下的
收益在别处（仓库可见性、常量随机化）。

## 12. `vmp-profile-func/runtime.vm` 的改动史（2026-11-11）

这一节只记 **我们改过的 profile 字段**，因为每次改动都对应一次真机事故。

| 字段 | 值变化 | 时间 | 原因 |
|---|---|---|---|
| `runtime.scope` | `module` → **`func`** | 2026-11-06 | 函数级隔离：每函数独立 dispatcher/opcode/handler，逆一套只能读一个 |
| `runtime.entry` | `call` → `inline`（2026-11-10）→ **回退 `call`**（2026-11-11） | 见右 | 见 §12.1 |
| `polymorph.scope` | `module` → **`func`** | 2026-11-06 | 同 `runtime.scope` |

### 12.1 为什么 `runtime.entry` 回退到 `call`

`inline` 是 2026-11-10 加上的，目的是消除 `bl <dispatcher>` 这个明文路标。
但它把整个解释器内联进每个被保护函数，**栈帧叠加**。

真机实测（消费方：artifact-pipeline + nox 锁箱 + Amice VMP）：

```
signal 11 (SIGSEGV), code 2 (SEGV_ACCERR), fault addr 0x...ff8
tid DefaultDispatch

xCrash maps:
  0x74252d0000-0x74252d1000  ---           [anon:stack_and_tls]  ← guard page
  0x74252d1000-0x74253d2670  rw-  0x107000  (栈本体 ≈1.03MB)
sp    = 0x74252d1000   ← 正好在 guard 上边界
fault = 0x74252d0ff0   = sp - 0x10
失败指令: stp xzr, xzr, [sp, -0x10]!
```

`DefaultDispatch` 是 ART 线程池线程，栈只有约 **1MB**（主线程 8MB）。
`inline` 之后 5 个被保护函数各自的解释器帧叠加 → 撑爆。

回退到 `call`：解释器独立成一个函数，被保护函数只留小而固定的栈帧。
代价是 `bl <dispatcher>` 路标回来了 —— 用可运行性换可发现性，这个取舍是对的。

> ⚠️ 若将来想再用 `inline`，**必须先在 1MB 栈的线程上验证**，
> 不能只看主线程跑得通。

### 12.2 一个反直觉的观测

改 `runtime.entry` 之前，`.ncx` 是 82,280 字节；改回 `call` 后降到 40,236。

看起来像"VMP 失效了"，实际不是 —— 之前 `.ncx` 涨的那部分是 **dex2c 产物的业务方法**
（`jni.k` 22KB 等）被段标记收进来的，与 VMP 无关。

**判断 VMP 是否生效不要看 `.ncx` 大小**，要看：
- `RUST_LOG=amice=debug` 里有没有 `skip function "xxx"`
- 目标常量是否从 so 里消失（如 splitmix64 的 `0xBF58476D1CE4E5B9`）
- `.text` 里有没有 `sub sp, #0x560` 级的 spill frame

## 13. 段权限硬约束的补充（2026-11-11，消费方实测反哺）

§12 记的是 profile 改动。这一节记 **`.ncx` / `.ncxr` 的用法约束**，
因为消费方（artifact-pipeline）在接 VMP 时踩了一个本仓库文档早就写过、
但只写给"改 nox 的人"看的坑。

### 13.1 `AGENTS.md` §2.2 的规则要再强调一遍

> **数据段不能用 `.ncx`** —— clang 拒绝让 `const` 数据进 AXR 段。

消费方的实际踩法（比 clang 报错更隐蔽）：

```c
/* 为了防 -Oz 常量传播，去掉了 const → 变成可写数据 */
static uint8_t key[8] __attribute__((section(".ncx"))) = {...};
```

**clang 不报错了**（不是 const 了），但**链接器把整个 LOAD 段标成 RWE**：

```
LOAD R-X  va=0x0      size=0x7b160
LOAD RWE  va=0x7f160  size=0xad98    ← .ncx 区域变成 RWX
```

Android 14+ 直接拒绝加载：

```
UnsatisfiedLinkError: dlopen failed: "libnc.so" has load segments
that are both writable and executable
```

**所以 §2.2 的规则不只是"clang 会报错"，更是"运行时会拒载"。**

### 13.2 段选择速查

| 内容 | 段 | 段权限 | 锁箱是否加密 |
|---|---|---|---|
| 函数（代码） | `.ncx` | AXR = `R-X` | ✅ |
| 常量 / 密钥 / 表 | `.ncxr` | AWR = `RW-` | ✅（`--section .ncx,.ncxr`） |
| **混放** | `.ncx` 里放数据 | **RWE** | ❌ Android 拒绝加载 |

⚠️ `.ncxr` 解锁后是 **可写** 的（RW-）。MAC 保护能挡住篡改，
但挡不住**读取** —— 密钥在运行时内存是明文，这是锁箱的本质限制。

### 13.3 给上游 amice 的三个补丁（本仓库无关，仅记录）

消费方为了让 VMP 能作用在自定义段里的函数，在自己的 amice fork 上加了：

| 补丁 | 解决的问题 |
|---|---|
| wrapper 继承 section | 否则函数被 VMP 后落到 `.text`，锁箱白做 |
| 跳过 `JNI_OnLoad` | 全局开关把它也 VMP 了 → 启动即 SIGSEGV |
| 豁免 `@llvm.used` | 否则想用 VMP 就得删 `used` → 函数被 gc → 加密段留死代码 |

**第三条与本仓库的 `NC_OBF` 宏有交互**：`nc_guard_boot.c` 的 `NC_OBF`
用 `noinline + annotate(...)`，不含 `used`，所以不受影响。
但如果将来给解密链函数加 `used/retain`，需要 amice 已豁免 `@llvm.used`
（即 bundle 版本 ≥ `v0.1.6-nox4`）。

完整记录见消费方 `artifact-pipeline/docs/so层防御/amice-fork改造记录.md`。

## 14. 关闭解密链 VMP（2026-11-12 的临时决定，**后来已恢复**）

> ⚠️⚠️ **状态提示：这一节记录的「关闭」是 2026-11-12 的临时状态。**
> **2026-11-13 已恢复**（`make-zip-lib.sh` 里 `nc_guard_xor|nc_guard_crypto`
> 分支重新启用 `_vmp=1`，且段布局改为 §15 所述）。
>
> **但 §14 的核心结论仍然成立**，而且很重要：
>
>   > VMP 保护「过程」无效（攻击者执行绕过），保护「逻辑」才有效。
>   > 判据：问一句「攻击者要的是结果还是逻辑」。
>
> 这就是为什么第一套 VMP 现在的定位是「提高理解成本」而非「防住绕过」，
> 也是为什么 2026-11-13 决定不加密 `.ncr`/`.nct`（见 §15.5）。

### 14.1 触发事件

一次**零信息逆向**（分析者未读本仓库任何源码）用 unicorn 模拟执行：

```
unicorn 加载 libnc.so
  → 从 .init_array 拿 constructor 地址（readelf -d，1 秒）
  → 让代码自己跑
  → 在 RC4 入口下钩子
  → 17 分钟拿到 boot_key 与 .ncxh 明文
```

**那 14 个 VMP 保护的函数，它一个都没读懂，但全部拿到了输出。**

### 14.2 为什么 VMP 挡不住

```
VMP 做的事：把函数体从「明文 ARM64」换成「字节码 + bl 解释器」
攻击者做的事：不读字节码，让解释器自己跑，在出口取结果
```

**VMP 保护的是「这段代码怎么写的」，不是「这段代码做什么」。**

而"解 `.ncx` / 拿 key"这类目标**根本不需要阅读**——跑一遍就有。

### 14.3 数据

| | arm64-v8a | armeabi-v7a |
|---|---|---|
| 旧（带 VMP） | 449,356 B | 481,016 B |
| 新（无 VMP） | **60,532 B** | **44,388 B** |
| 减少 | **-86.5%** | **-90.8%** |

| 目标文件 | 旧 | 新 |
|---|---|---|
| `nc_guard_crypto.o` | 376,448 B | **10,456 B** |
| `nc_guard_xor.o` | 24,064 B | **1,232 B** |
| VM 子段数 | 235 | **0** |

14 个函数原始指令合计约 180 条 ≈ 720 B → **VMP 膨胀 520 倍**。

成品 `libnc.so`：856,152 B → **642,664 B**（-25%）。

### 14.4 关键区分：两种 VMP，价值完全不同

| | 第一套（本仓库，已关） | 第二套（消费方 sig_check，保留） |
|---|---|---|
| 保护对象 | 解密链：`ncg_boot_key` / `ncguard_stub_recover` 等 | 签名校验逻辑：`derive_expected` / `sig_verify` 等 |
| 攻击者要什么 | **结果**（k_stub、master） | **理解逻辑**（才能改校验） |
| VMP 有效吗 | ❌ **无效**（执行一遍就有结果） | ✅ **有效**（必须逆 VM 才能改） |

**判据：问一句「攻击者要的是结果还是逻辑」。**
- 要结果 → VMP 无效
- 要逻辑 → VMP 有效

### 14.5 关掉之后仍然有效的防护（不要一起关）

| 防护 | 机制 | 与 VMP 的关系 |
|---|---|---|
| 六段锁箱 | `.ncx`/`.ncxr`/`.ncxh`/`.ncxhr`/`.nck`/`.ncks` | 无关 |
| **`.text` CRC 自绑定** | `k_stub ^ fold(crc32(.text))`，改一位全链崩 | 无关 |
| `NC_OBF` 宏 | `nc_guard_boot.c` 的 3 个函数（flatten/mba/shuffle 等 5 项） | **无关**，走 annotate 路径 |
| HKDF label 密文化 | `ncg_label_*` 四张表 | 无关 |
| 元数据清理 | `--strip-meta` | 无关 |

**特别说明**：`NC_OBF` 走的是 `annotate("+flatten")` 等，
与本文件的 `AMICE_VM_VIRTUALIZE`（文件级）是两套机制，**关闭 VMP 不影响它**。

### 14.6 怎么恢复

把 `make-zip-lib.sh:136-139` 的 case 分支换回来：

```bash
case "$f" in
    nc_guard_xor|nc_guard_crypto) _vmp=1 ;;
    *) _vmp=0 ;;
esac
```

恢复后必须验两件事：
```bash
./scripts/check-obf.sh <产物>    # VM 子段数 > 0
# 真机 selftest
```

**为什么保留 case 结构而不是删掉**：VMP 开关逻辑（profile 选择、
bundle NDK 校验）在下面的 `if` 里，删了分支将来恢复时会漏掉 profile 检查
→ 静默退回 module 级共享。

## 15. 段架构最终版（2026-11-13，实测为准）

> **本节是段布局的唯一真相源。** 之前的 §15 草案（数据段分离）已被推翻，
> 内容全部重写。若与其他文档冲突，以本节 + 产物实测为准。

### 15.1 一句话架构

**两套 VMP，各有「解释器 + 字节码 + 数据表」三件套，放在六个段里。**
`.ncx` 不是 VMP 段，是业务代码的加密段 —— 里面有 VMP 壳，但逻辑已被抽走。

### 15.2 段对照表（实测，arm64 产物）

| 段 | 大小 | 权限 | 加密 | 是什么 | 属于 |
|---|---|---|---|---|---|
| `.ncx` | 39 KB | `r-x` | ✅ | **代码**：业务函数 + 8 个 VMP 壳（wrapper） | 消费方 |
| `.ncxr` | 96 B | `r--` | ✅ | 数据：签名表 `SIG_SALT` / `SIG_HASH_STORED` | 消费方 |
| `.ncxh` | 3.8 KB | `r-x` | ✅ | **代码**：解锁器本体 | nox |
| `.nct` | 104 KB | `r-x` | ❌ | **代码**：第二套**解释器**（dispatcher） | 第二套 |
| `.ncv` | 128 KB | `r--` | ❌ | 数据：第二套**字节码** + 常量池 | 第二套 |
| `.ncw` | 1.1 KB | `rw-` | ❌ | 数据：第二套 descriptor / native 表 | 第二套 |
| `.ncr` | 142 KB | `r-x` | ❌ | **代码**：第一套**解释器** | 第一套 |
| `.ncq` | 95 KB | `r--` | ❌ | 数据：第一套**字节码** | 第一套 |
| `.ncs` | 1.3 KB | `rw-` | ❌ | 数据：第一套 descriptor / native 表 | 第一套 |

**判断「代码还是数据」的可靠方法**：`readelf -SW` 看权限列，
带 `x` 的是代码，不带的是数据。**不要靠段名猜。**

**记忆锚点**：
```
.nc r  + .nc q  + .nc s   = 第一套（解释器 + 字节码 + 表）
.nc t  + .nc v  + .nc w   = 第二套（解释器 + 字节码 + 表）
.nc x  + .nc xr  = 业务代码 + 签名表（不是 VMP 段）
.nc xh + .nc xhr = 解锁器 + master
```

### 15.3 两套 VMP 分别是什么

| | 第一套 | 第二套 |
|---|---|---|
| 保护对象 | 本仓库的解密链（`ncg_boot_key` / `ncg_stub_recover` 等） | 消费方签名校验（`sig_check.c` 的 11 个函数） |
| 编译方 | nox（`make-zip-lib.sh`，预编译进 `libnox.a`） | 消费方（`protect.sh`） |
| 解释器 | `.ncr` | `.nct` |
| 字节码 | `.ncq` | `.ncv` |
| 数据表 | `.ncs` | `.ncw` |
| 段名从哪来 | `AMICE_VM_INSN_SECTION=".ncr"` / `AMICE_VM_DATA_SECTION=".ncq,.ncs"` | `AMICE_VM_INSN_SECTION=".nct"` / `AMICE_VM_DATA_SECTION=".ncv,.ncw"` |

**⚠️ 两套段名必须不同**：链接进同一个 so。同名会混淆 →
第一套解释器按 `adr` 偏移找表却找到第二套的 → VM 寄存器读垃圾 → SIGSEGV
（2026-11-13 实测，pc 落在 `.ncr+0x5bc8`，`x20=0x48416df089015220` 全是垃圾）。

### 15.4 执行链

```
.nc x  壳（wrapper）
   │  sub sp,#0xd0 ; 4×movk 拼 token ; bl <解释器>
   ↓
.nc t / .nc r  解释器
   │  token → 4 步运算 → fn_index
   │  fn_index → 查 .ncw/.ncs 第 fn_index*8 行
   │            → code_offset / code_len / bytecode.key
   ↓
.nc v / .nc q  字节码（逐条 opcode 执行）
   │  每个 opcode → 查 .ncw/.ncs 的 handler 指针 → 跳到 .text 里执行
   ↓
.text  151 个 handler 的实现（16~20 字节的小桩，全是明文）
```

**关键：handler 的「语义」在 `.text`（明文），「指向」在 `.ncs`/`.ncw`（明文）。**

### 15.5 为什么只有 `.ncx`/`.ncxr`/`.ncxh` 加密

**实测收益/代价：**

```
段        大小      加密后 APK 压后    不加密 APK 压后    差额
.nc v   128,533        128 KB            37 KB          +91 KB
.nc t   104,200        104 KB            45 KB          +59 KB
.nc x    39,116         39 KB            17 KB          +22 KB
```

加密段熵 8.0，**zlib 完全压不动**（100.0%）。这是硬开销。

**保留加密的判断依据：**

| 段 | 加密 | 理由 |
|---|---|---|
| `.ncx` | ✅ | 里面有 10 个 dex2c 业务方法（明文 ARM64，解开就能读）+ 8 个壳的 descriptor token |
| `.ncxr` | ✅ | 96 B 签名基准值 —— 解开它等于拿到「正确答案」 |
| `.ncxh` | ✅ | 解锁器本体，静态读它等于拿到算法 |
| `.nct`/`.ncv` | ❌ | 解释器是公开 VM 规则（Amice 开源可抄）；字节码的强度来自 VMP 本身 |
| `.ncr`/`.ncq` | ❌ | **结构性约束**：解 `.ncx` 的钥匙要执行第一套解释器，加密即自锁 |
| `.ncs`/`.ncw` | ❌ | **结构性约束**：`R_AARCH64_RELATIVE` 重定位槽，加密会覆盖链接器填的指针 → SIGILL |

### 15.6 攻防成本模型（2026-11-13 修正）

**早期判断错了：假设攻击者会直奔最贵的路（逆 VM）。实际不会 ——
合格的逆向者按性价比排序。**

```
成本从低到高：
① strings / objdump 扫明文                     秒级
② 破锁箱解 .ncx                                分钟~小时
③ frida hook 解释器看执行流                    分钟（不需要懂 VM）
④ 逆向 VM 语义（读 .nct/.ncr + 逆 handler）    天~周
```

**所以 `.ncx` 加密的真实价值：**

> 把攻击者从 ① 逼到 ③ 或 ④。这两条都比静态读贵一个量级，
> 而 ③ 还要过 `env_check.c` 的反调试。

**而 `.nct`/`.ncv` 明文不等于「门开着」** —— 它只是让最贵的第 ④ 步
少了一个前置开销。真正的前置防线（`.ncx` 加密）还在。

### 15.7 当前架构的三个真问题（如实）

**① `boot_key` 的输入全是静态数据**

```c
ikm = CRC32(.text[0:16384]) || .text[0:16] || .text[16368:16384]
boot_key = HKDF(ikm, SALT, "nc-boot-v1")
```

`.text` 就在 APK 里 → **这不是密钥派生，是可复现的哈希。**

2026-11-13 实测：纯静态（不运行一行代码）从 APK 算出 `boot_key` →
解 `.ncks` → 拿 `k_stub` → 解 `.ncxhr` → 拿 `master` → 解 `.ncx`/`.ncv`。
全程约 40 分钟。

**② 加密的量和收益不成比例**

```
加密 43 KB（.ncx/.ncxr/.ncxh）
明文 470 KB（两套 VMP 的解释器+字节码）
```

**③ 最强防护（VMP）依赖明文解释器**

攻击者读一遍 `.ncr`/`.nct`（明文）就懂 VM 规则，然后按规则解 `.ncq`/`.ncv`。

> **470 KB 的 VMP 数据，安全性等于 246 KB 明文解释器的安全性。**

### 15.8 若要提升强度，按性价比排序

| 优先级 | 改什么 | 收益 | 代价 |
|---|---|---|---|
| P0 | `boot_key` 引入运行期秘密（设备指纹等） | 断掉整条链的静态起点 | 兼容性风险 |
| P1 | 解释器搬进加密段 + 私有映射执行 | 解释器不落盘明文 | 要改 Amice，工程量大 |
| P2 | 加强反调试（frida/xposed 检测） | 挡住目前最有效的攻击 | `env_check.c` 有基础 |

**⚠️ P0 的边界**：运行期秘密必然在内存，有 frida 就能拿。它把
「静态 40 分钟」变成「动态 40 分钟 + 需要真机」—— 对批量工具是实质障碍，
对有心人不是。不要高估。

### 15.10 改这块代码前必须知道的五条

1. **段名是格式契约**，改名 = 所有历史产物解不开。要加段就在
   `nc_guard_layout.h` 登记并同步 `so-section-lock.py`。
2. **`set_section` 会移动 global 的落点**。动之前确认那批数据有没有重定位
   （`readelf -r` 看 `r_offset` 是否落在该段）。
3. **同名的段被处理两次 = RC4 两次 = 还原成明文**，且 MAC 会拼两遍。
   2026-11-13 因此 SIGILL，症状完全不指向段列表。
   段列表必须用数组 + 去重断言（`protect.sh` 已改）。
4. **新增全局变量会改 `.bss` 布局** → `.ncxhr`/`.bss` 的页面归属变化 →
   `ncg_page_has_writable_neighbor` 判定变 → SIGILL。报告缓冲因此放【栈上】。
5. **新增 `.c` 文件要同步四处清单**（`test.sh` 通配符已自动、
   `make-zip-lib.sh` 的 `LIB_SRCS`、`nox` CLI 的 `_guard_sources()`、
   `protect.sh` 的拷贝）。V14 断言会检查。
