# 流程文档 — nox 怎么用、怎么改、怎么发版

> 面向"要动手的人"。只讲操作步骤与验收判据，不讲设计理念（那在 `AGENTS.md`）。
> 与代码冲突时以代码为准。

## 0. 三种用法，先选对

| 你要做什么 | 用哪条路 | 见 |
|---|---|---|
| 给自己的 C 代码加 so 段加密 | `./nox protect` | §1 |

## 1. 一条命令：`nox protect`

### 最小可用

```bash
./nox protect mycode.c --apk app-release.apk -o libmy.so
```

这条命令内部依次做：编译 → 一级锁箱（`.ncx`）→ 二级锁箱（`.ncxh`）→
元数据清理（`.eh_frame`/`.comment`/`.debug_*`）→ strip。

> ⚠️ 元数据清理这一步是 **2026-11-06 才补进 CLI 的**。此前 `nox protect`
> 只做前三步，产物里留 `.eh_frame`（实测 2108 B / **70 个 FDE**，每个 FDE
> 给出一个函数的精确起止地址）—— `AGENTS.md` §5.4 说"必须清理"，但最常用
> 的这条命令没做，只有手工三步锁箱的人有保护。`test.sh` 的 **V9** 现在钉住
> 这一点（验产物，不验日志）。若你手上的旧产物有 `.eh_frame`，重跑一次
> `nox protect` 即可。

### 前提：必须有【已签名】的 APK

密钥由 APK 证书派生（`k_so = HKDF(master, SHA256(certDER), "nc-so-v1"+包名)`）。
运行期从已安装的 APK 重读证书，**读不到就拒绝解密**（返回 `-12`）。

| 场景 | 能否用 |
|---|---|
| Android App 里的 so | ✅ |
| 独立 so / Linux 程序 | ❌ 没有 APK 证书 |

### 你的代码要先标记

nox 不加密"没标记的东西"（没有 `.ncx` 段就没有可加密的单元）：

```c
__attribute__((section(".ncx"), used, retain))
int my_secret(int a) { return (a ^ 0x5A) * 3; }
```

- `used` 防被优化掉
- `retain` 防 `--gc-sections` 回收
- 常量数据不能放 `.ncx`（clang 会报 `causes a section type conflict`），要用 `.ncxr`

或让工具自动打标：

```bash
python3 scripts/so-guard/so_section_mark.py <源码目录> --rule <规则名> -v
```

### 交叉编译（没有系统 clang 时）

```bash
export ANDROID_NDK_HOME=/path/to/ndk
./nox protect mycode.c --apk app.apk -o libmy.so --abi arm64-v8a
```

### 验收

```bash
# ① 六个加密段必须都在
readelf -SW libmy.so | grep -E '\.ncx|\.nck'
#   期望看到 6 个：.ncx .ncxr .ncxh .ncxhr .nck .ncks

# ② .ncx 必须是密文（熵接近上限，不是明文指令）
python3 - <<'PY'
import sys, math, struct
from collections import Counter
d = open('libmy.so','rb').read()
off=struct.unpack_from('<Q',d,0x28)[0]; es=struct.unpack_from('<H',d,0x3a)[0]
en=struct.unpack_from('<H',d,0x3c)[0]; ex=struct.unpack_from('<H',d,0x3e)[0]
sh=lambda i: struct.unpack_from('<IIQQQQIIQQ',d,off+i*es)
st=sh(ex)[4]
for i in range(en):
    s=sh(i); nm=d[st+s[0]:d.index(b'\0',st+s[0])].decode('latin1')
    if nm in ('.ncx','.ncxh'):
        b=d[s[4]:s[4]+s[5]]; c=Counter(b); n=len(b)
        e=-sum((v/n)*math.log2(v/n) for v in c.values())
        lim=math.log2(min(n,256))
        print(f"  {nm}: {n}B 熵={e:.3f} 上限={lim:.3f} {'OK' if e>lim-0.8 else 'FAIL'}")
PY

# ③ .dynsym 里不该有业务函数名
readelf --dyn-syms libmy.so | grep -c 'Java_com_'   # 期望 0 或只有 JNI_OnLoad

# ④ strings 不该有明文语义
strings libmy.so | grep -iE 'nc-boot-v1|nc-so-v1'   # 这几个 label 仍会命中，见 §5
```

## 2. 手工锁箱（CMake/Gradle 项目）

`nox protect` 是"一条命令"，但它假设你用它自带的编译参数。已有项目通常要保持自己的
`Android.mk`/`CMakeLists.txt`，那就分三步手工做。

### 2.1 链接加密设施

**静态库形态（推荐，C 源码不外泄）**

```makefile
# Android.mk
LOCAL_LDFLAGS += -Wl,--whole-archive \
                 $(NOX)/lib/$(TARGET_ARCH_ABI)/libnox.a \
                 -Wl,--no-whole-archive
```

> ⚠️ **`--whole-archive` 不能省**：`ncguard_unlock` 是 `constructor`，无人显式引用
> → 链接器按需拉取时整个丢掉 → 六个加密段塌成一个。
> 实测不加时 `.ncx/.ncxh/.nck/.ncks` 全消失。

**源码形态**

```makefile
LOCAL_SRC_FILES += $(NOX)/nc_guard_boot.c $(NOX)/nc_guard_probe.c \
                   $(NOX)/nc_guard_key.c  $(NOX)/nc_guard_paths.c \
                   $(NOX)/nc_guard_xor.c
LOCAL_CFLAGS += -DNC_GUARD_SECTIONED -I$(NOX)
```

> `-DNC_GUARD_SECTIONED` 不加则 `__attribute__((section()))` 全不生效。

### 2.2 锁箱三步，顺序不能错

```bash
NOX=../nox/scripts/so-guard
APK=app-release.apk
SO=libs/arm64-v8a/libmy.so

# ① 一级锁箱：加密 .ncx（有 .ncxr 时一并加密，用逗号分隔）
python3 $NOX/so-section-lock.py $SO $SO --section .ncx,.ncxr --from-apk $APK

# ② 二级锁箱：把 unlock 本体也加密进 .ncxh
python3 $NOX/so-section-lock.py $SO $SO --lock-head

# ③ 元数据清理：删 .eh_frame / .comment / .debug_*
python3 $NOX/so-section-lock.py $SO $SO --strip-meta
```

> ⚠️⚠️ **这三步是互斥分支，不能合并传参**。
> `so-section-lock.py` 的实现是：
> ```python
> if args.strip_meta: return strip_meta(...)
> if args.lock_head:  return lock_head(...)
> return lock(...)
> ```
> 传了 `--lock-head` 就**只**做二级锁箱，一级加密被跳过。
> 实测症状：`.ncx` 里仍是明文 ARM64 指令（熵 5.5），看起来"锁了"实际没锁。

> ⚠️ `--strip-meta` 必须在 `--lock-head` **之后**：objcopy 会重写 ELF，
> 而锁箱期写进 `.nck`/`.ncks` 的是链接期 `sh_addr`，任何挪动都会让运行期基址计算全崩。

### 2.3 用 `nox build` 先试编译

```bash
./nox build mycode.c -o libmy.so --abi arm64-v8a    # 只编译，不加密
```

适合排查"编译不过"和"锁箱不过"的区别。

## 3. 改 nox 自身

### 3.1 改完必跑

```bash
./test.sh      # V1–V9，约 1–2 分钟
```

判据是 **0 失败**，不是某个固定数字 —— 断言数随环境分支变化
（`.ncxr` 缺失、`.a` 形态都会 skip）。当前源码形态 + ARM 宿主实测
**21 通过 0 失败**。

失败项含义（`test.sh` 里的 Vn 编号）：

| 项 | 验什么 |
|---|---|
| V1 | 源码能编 |
| V2 | 五个段齐全（`.ncxr` 视业务代码而定，可缺） |
| V3 | 锁箱后 `.ncx` 是密文（熵值） |
| V4 | 路径明文扫不到 |
| V5 | 篡改密文 → 段不可执行 |
| V6 | **完整解锁链路**：未篡改时 dlopen 能拿到正确结果 |
| V7 | `.ncxr` 与 `.bss` 同页时的 mprotect 处理 |
| V8 | `--strip-meta` 删干净且段地址不变（手工调用路径） |
| V9 | **`nox protect` 自带元数据清理**（CLI 全链路，验产物） |

> V5/V6/V7 依赖 `dlopen` 执行。判据是 `CAN_EXEC`：**源码形态 = 1**
> （产物是本机架构，真跑，与宿主架构无关）；**静态库形态 = 0**
> （`.a` 是 ARM，x86 宿主跑不了）→ 跳过并打印"静态验证"。
> 真机验证不能省。
>
> ⚠️ 注意 V8 与 V9 的分工：V8 验"手工调 `--strip-meta` 有没有效"，
> V9 验"最常用的那条命令有没有自动做"。`AGENTS.md` §5.4 的"必须"
> 只有落在 V9 上才算真的堵住 —— 2026-11-06 之前 V8 一直绿，而
> `nox protect` 的产物里 `.eh_frame` 完整保留。

### 3.2 拆分/新增 .c 文件时，四处清单必须同步

这是本仓库最容易漏的地方，**已经漏过两次**（2026-11-06 拆
`nc_guard_xor.c` 时先漏了 nox 内三处、补完又漏了消费方一处）。

```bash
# 一条命令找全（在 nox 仓库根执行）
grep -rn "nc_guard_boot.c" \
  --include="*.sh" --include="*.yml" --include="*.py" --include="nox" . \
  ../artifact-pipeline/scripts ../artifact-pipeline/.github 2>/dev/null
```

| # | 位置 | 漏了会怎样 |
|---|---|---|
| 1 | `test.sh` → `guard_compile()` | 链接缺符号，V6/V7 报 NOOPEN |
| 2 | `scripts/make-zip-lib.sh` → `LIB_SRCS` | 打包时漏编该文件 |
| 3 | `nox`（CLI）→ `GUARD_SRCS` | CLI 编译缺符号 |
| 4 | **`../artifact-pipeline/scripts/pipelines/protect.sh`** | **消费方的源码形态拷贝清单；漏了会在消费方构建时链接失败** |

> ⚠️ 第 4 处不在本仓库里，最容易漏。它验的是"源码形态下要把哪些 `.c`
> 拷进 NDK 工程"。判据来源是本仓库的 `LIB_SRCS`。
>
> 消费方已有断言 `test_nox_copy_list.py`（8 条）钉住这件事，但它需要
> `../nox` 才能跑 —— CI 未 clone nox 时会跳过。

`make-zip-src.sh` 是遍历目录，不用改。

**教训**：`grep` 的范围必须跨仓库。只在本仓库 grep 会漏掉消费方，
而消费方的失败往往更晚才暴露（构建期甚至运行期）。

### 3.3 改测试必须做反向验证

新增"篡改/拒绝/失败"类断言时，**故意把代码改坏，确认断言真的会红**。
否则就是恒真断言（本项目踩过三次假绿，见 `AGENTS.md` §3.2）。

## 4. 发版

### 4.1 两种包，用途不同

```bash
# 静态库形态（当前默认，C 源码不外泄）
ANDROID_NDK_HOME=/path/to/ndk ./scripts/make-zip-lib.sh v1.2.3

# 源码形态（给要审查/改代码的人）
./scripts/make-zip-src.sh v1.2.3
```

产物在 `dist/nox-<ver>.zip`，包内 `nox/VERSION` 自报版本。

### 4.2 带代码混淆发版

**两条路都能出混淆版，选一条即可。**

#### 路线 A：打 tag（推荐，符合"打标签就出正式包"的预期）

```bash
git tag v1.2.3-obf          # 注意 -obf 后缀
git push origin v1.2.3-obf  # CI 自动：拉 bundle → 混淆编译 → 打包 → 发 Release
```

**判定规则**：tag 名含 `-obf` → 自动开混淆；不含 → 普通版。**只有这一个后缀。**

```
git tag v1.2.3       && git push --tags   → 普通版（不混淆）
git tag v1.2.3-obf   && git push --tags   → 混淆版
```

⚠️ **版本号必须带后缀**：这是"这版有没有混淆"的唯一记录，看 tag 名就知道，
不依赖任何外部配置。

#### 路线 B：手动 dispatch（本地出包时用）

```bash
AMICE_BUNDLE=/path/to/amice-android-ndk-r29-linux-x86_64 \
  ANDROID_NDK_HOME=/path/to/ndk \
  ./scripts/make-zip-lib.sh v1.2.3-obf
```

设了 `AMICE_BUNDLE` 就开混淆，没设就普通编译（默认，向后兼容）。

或者点 Actions 的 `release` workflow，勾 `obfuscate: true`。

#### 为什么打 tag 这条路必须存在（2026-11-06 修）

此前混淆只由 `workflow_dispatch` 的 `inputs.obfuscate` 控制。而 **push tag
触发时 inputs 全为空**，`inputs.obfuscate == true` 恒假 → 打标签永远出
普通版。接手的人问"怎么发混淆版，打标签不就好了吗"—— 按当时的实现，
答案是"打标签不行，必须手动点"，而且文档里没写清楚。

现在两条路都通，且 tag 那条符合直觉。

**为什么混淆必须在发布时做**：本仓库发的是已编译的 `libnox.a`。Amice 是编译期
pass，只能在编译源码时生效 —— 消费方拿到 `.a` 后无法再混淆其中函数。
实测过这个空转：消费方开 `AMICE_MBA=true` 后，`ncg_boot_key` 的反汇编与
无混淆版**逐条指令一致**。

### 4.3 混淆引擎：Amice

#### 4.3.1 它是什么

**LLVM Pass 插件**，通过 `-fpass-plugin=<path>/libamice.so` 加载。
不需要重新编译 LLVM —— 这是它相对 OLLVM 的主要优势（OLLVM 要自编译整套
clang 工具链，stock NDK clang 不认识 `-mllvm -fla`）。

版本约束（**硬要求，错配是段错误不是报错**）：

| NDK | clang | 需要的插件 |
|---|---|---|
| r27d | 18.x | `libamice-android-ndk-r27d-*.so` |
| r29 | 21.x | `libamice-android-ndk-r29-*.so` |

插件走 LLVM 的 C++ ABI，主版本错配时 clang 直接 SIGSEGV（`exit code 139`），
链接期拦不住。实测：NDK r27d 的 clang 18 加载 r29 插件 → clang frontend crashed。

**所以混淆模式下必须用 bundle 自带的 NDK**（`make-zip-lib.sh` 已自动处理：
设了 `AMICE_BUNDLE` 就从 `<bundle>/android-ndk-*` 取 clang）。

插件依赖宿主 `libLLVM.so`，而官方 NDK **不带**它（`find $NDK -name libLLVM*`
为空）。所以必须 `LD_LIBRARY_PATH=<bundle>/amice/llvm-lib`，否则报：

```
error: unable to load plugin 'libamice.so': libLLVM.so: cannot open shared object file
```

#### 4.3.2 Amice 提供的全部 pass（17 个）

来源：Amice `docs/FunctionAnnotations_zh_CN.md`（按该文件逐条核对，共 17 个）。
**我们只用了 6 个**（见 4.3.3）。

| pass | 注解名 | 做什么 | 强度 | 体积代价 | 我们用吗 |
|---|---|---|---|---|---|
| 控制流扁平化 | `+flatten` | 把基本块顺序与分支结构打散成状态机 | **高** | +30~60% | ✅ |
| 混合布尔算术 | `+mba` | 算术/逻辑运算替换成等价但难读的形式 | 中 | +10~20% | ✅ |
| 基本块乱序 | `+shuffle_blocks` | 扰动函数内基本块的物理顺序 | 中 | ~0 | ✅ |
| 基本块拆分 | `+split_basic_block` | 把一个基本块拆成多个更小的 | 中 | 随 `num` 线性 | ✅ |
| 函数分片 | `+basic_block_outlining` | 把基础块提取为独立子函数（BB2Func） | 中 | 中 | ❌ |
| 间接调用 | `+indirect_call` | 改写直接函数调用（静态看不到谁调谁） | 中 | ~0 | ✅ |
| **指令级 VMP** | `+vm_virtualize` | 函数提升为 VM bytecode + 生成解释器 | **极高** | **+300~2000%** | ✅（仅 1 个函数） |
| 虚假控制流 | `+bogus_control_flow` | 插入假分支 | 高 | 翻几倍 | ❌ |
| VM 控制流平坦化 | `+vm_flatten` | 平坦化 + 索引操作加密 | 高 | 大 | ❌ |
| 函数包装 | `+function_wrapper` | 调用点外包一层代理 | 中 | 小 | ❌ |
| 间接跳转 | `+indirect_branch` | 直接跳转改间接 | 中 | 小 | ❌ |
| 常参克隆 | `+clone_function` | 常量实参特化克隆 | 低 | 中 | ❌ |
| 别名访问 | `+alias_access` | 指针链访问 | 低 | 小 | ❌ |
| 延时偏移加载 | `+delay_offset_loading` | 打散"基址+常量偏移"模式 | 中 | 小 | ❌ |
| Switch 降级 | `+lower_switch` | switch → if-else 链（给 flatten 铺路） | 前置变换 | 小 | ❌ |
| 参数结构化 | `+param_aggregate` | 参数聚合混淆 | 中 | 小 | ❌ |
| 自定义调用约定 | `+custom_calling_conv` | 改变参数传递方式 | — | — | ❌ **当前不可用**（文档标"预留实现"） |

#### 4.3.3 我们实际用哪几个，为什么

**`NC_OBF`（`nc_guard_boot.c`，用于 `ncg_boot_key` / `ncg_stub_recover`）**

```c
__attribute__((noinline,
  annotate("+flatten"),
  annotate("+mba"),
  annotate("+shuffle_blocks"),
  annotate("+split_basic_block"),
  annotate("+indirect_call")))
```

| 选它的理由 |
|---|
| `+flatten` —— 唯一能改变控制流结构的，是质变。不加它，MBA 只是"跳过去还能看到原指令" |
| `+mba` —— 算术等价替换，风险最低，做基础噪声 |
| `+shuffle_blocks` / `+split_basic_block` —— 打乱布局、增大 CFG 重建成本，体积代价小 |
| `+indirect_call` —— 打断调用链，静态看不到"谁调了谁" |

**不选的**：

| pass | 为什么不选 |
|---|---|
| `+vm_virtualize` | 见 4.3.4 —— annotate 会与它冲突 |
| `+bogus_control_flow` | 虚假分支让体积翻几倍，且关键路径上有实打实的执行开销 |
| `+vm_flatten` | 体积/编译开销大，且 flatten 已覆盖控制流 |
| `+clone_function` / `+alias_access` | 收益限表达式局部，对"读懂解密链"帮助很小 |
| `+function_wrapper` | 只加一层跳板，静态跟一下就穿过去了 |
| `+basic_block_outlining` | 拆出的子函数会进 `.dynsym`（除非 hide），且与 flatten 的作用重叠 |

**`NC_OBF_VMP`（`nc_guard_xor.c`，只用于 `ncg_xor_key`）**

```c
/* 文件级开关，不是 annotate */
AMICE_VM_VIRTUALIZE=true "$CC" -c nc_guard_xor.c -o nc_guard_xor.o
```

VMP 的效果（实测，同一函数 VMP 前后）：

| | VMP 前（210 条） | VMP 后（31 条 + 22720 字节 VM 运行时） |
|---|---|---|
| 循环 | `cmp x8,#0x8` + `b` 清晰可见 | ❌ 消失 |
| 查表 | `ldrb w11,[x10,x8]` | ❌ 消失 |
| 判断 | `cmp x8,#0x3` + `cset` | ❌ 消失 |
| 剩下什么 | 完整算法 | `sub sp,sp,#0xc0`（VM 帧）+ 3 个 64 位常量 + `bl 解释器` |

#### 4.3.4 为什么 VMP 只用于一个函数

**① VMP 与 annotate 互斥（这是硬限制）**

annotate 会把函数地址写进 `@llvm.global.annotations` 表，`vm_virtualize`
因此判定该函数 `has non-call address uses` 并**静默跳过**。

实测日志（必须开 `RUST_LOG=amice=debug` 才看得到）：
```
skip function "ncg_xor_key": function has non-call address uses
```

Amice 只提供两种启用方式：annotate（逐函数，但有上述冲突）或
`AMICE_VM_VIRTUALIZE`（整个编译单元）。**没有"按函数名指定"的途径。**

→ 所以把要 VMP 的函数拆到独立文件，对该文件用文件级开关。
`nc_guard_xor.c` 就是这么来的（只含 `ncg_xor_key` 一个函数）。

**② 另两个函数拆不动（依赖太重）**

| 函数 | 依赖 | 障碍 |
|---|---|---|
| `ncg_boot_key` | `ncg_slot_read` / `ncg_stub_find_text` / `ncg_boot_crc32` / `ncg_wipe` / `khkdf_sha256` | 要连带搬 7 个函数 |
| `ncg_stub_recover` | 上面全部 + `ncg_ctr_xor` / `ncg_rd32` / `khmac` / `dladdr` / `mprotect` | 138 行 + 时序敏感 |

**关键阻塞点**：`ncg_slot_read` 靠 `&ncg_stub_slot` 的 PC 相对地址反推镜像基址：

```c
uintptr_t img_base = (uintptr_t)&ncg_stub_slot - stub_sh_addr;
```

`ncg_stub_slot` 现在是 `static`（`.ncks` 段本体）。改成跨 TU 的外部符号后，
PC 相对寻址可能变成 GOT 间接寻址 → 基址反推错 → 整个解锁链失效。
**这个必须先单独验证。**

**③ 体积代价**

`nc_guard_xor.o`：1~2KB（普通）→ 22720 字节（VMP），单函数 20 倍。
整个 `libnox.a`：60858 → 81534 字节（+34%）。

#### 4.3.5 怎么判断混淆/VMP 真的生效

**不要看"配置里开了"就当生效。也不要只看"指令数变多变少"。**

##### 先记住一个反直觉的事实

同一个 `ncg_xor_key`（源码 8 行），实测三种状态：

| 状态 | `.o` 体积 | `ncg_xor_key` 指令数 | **VM 子段数** | 符号数 |
|---|---|---|---|---|
| 无混淆 `-Oz` | 1280 B | **15** | **0** | 2 |
| MBA+FLA | ~2 KB | 210（文档记录，未复测） | 0 | 2 |
| **VMP** | **22720 B** | **31** | **14** | 2 |

**指令数不能当判据**：VMP 是 `31`，无混淆是 `15` —— VMP 只比它多 16 条，
比 MBA+FLA 的 210 少得多。当年"看到数字变小就以为被跳过"的教训是真的，
但反过来"看到数字变大就以为生效"同样错。

##### 唯一可靠的判据：`nc_guard_xor.o` 里有没有 VM 子段

VMP 会在目标文件里生成一组独立命名的段：

```bash
cd /tmp && ar x <nox>/so-guard/lib/arm64-v8a/libnox.a
readelf -SW nc_guard_xor.o | grep 'L\.L__'
```

| 结果 | 判定 |
|---|---|
| 输出 **14 行**（`.text..L.L__<hash>` / `.rodata..L.L__<hash>` …） | ✅ VMP 生效 |
| 输出 **0 行** | ❌ 没 VMP（普通编译或被跳过） |

这是结构性的：只有 VMP 才会把解释器和字节码拆成独立单元，普通编译
不会产生 `.L.L__<16 位 hash>` 这种段名。**不依赖任何指令数阈值。**

```bash
# 一条命令判断（推荐，2026-11-06 新增）
./scripts/check-obf.sh <libnox.a>
#   逐目标文件打印 VM 子段数与体积，结论给"生效/未检出"
#   退出码 0 = 生效, 1 = 未检出 → 可直接用于 CI 断言

# 手动等价做法
cd /tmp && ar x <nox>/so-guard/lib/arm64-v8a/libnox.a
readelf -SW nc_guard_xor.o | grep -c 'L\.L__'
#   14 行 → VMP 生效（.text..L.L__<hash> / .rodata..L.L__<hash> …）
#   0 行  → 没 VMP
stat -c%s nc_guard_xor.o
#   22720 → VMP；1280 → 无混淆（差 17 倍，单调可靠）
```

配套两条辅助判据（都只在 `.o` 上成立）：

```bash
llvm-nm nc_guard_xor.o          # 两种状态都只有 2 个符号
                                # （NCG_XOR_FRAG + ncg_xor_key）
```

##### ⛔ 不要在 `libnc.so` 上 grep VMP 特征 —— 2026-11-06 实测是误判源

文档曾写过这条"全局特征"判据，**在链接后的 so 上完全失效**：

```bash
# ❌ 这两条都不要用（在 libnc.so 上）
llvm-objdump -d libnc.so | grep -cE 'sub .+#0xc0'                  # 实测 9
llvm-objdump -d libnc.so | grep -cE 'movk.+#0x[0-9a-f]+, lsl #48'  # 实测 56
```

实测反例（`protected_unsigned_sign.apk` 里的 libnc.so，确认是 VMP 版）：

| grep 命中 | 真实来源 | 与 VMP 的关系 |
|---|---|---|
| `sub sp,sp,#0xc0` ×9 | `nc_guard_key.c` 里 1.6 KB 证书 DER 缓冲的普通栈帧 | **无关** |
| `movk lsl #48` ×56，第一处是 `0x2067`+`0x3234` | `"APK Sig "` / `"Block 42"` —— APK 签名块 magic 常量 | **无关** |

**根因**：这些特征在单个 `.o` 里才有区分度。链进 so 之后，
`nc_guard_key.c` 的证书解析、`ncg_boot_key` 的大栈帧都会产生同样的指令。
**在 so 上 grep 等于在噪声里找信号**，两个方向都会误判：
- 以为没 VMP → 实际有（被无关代码的特征误导）
- 以为有 VMP → 实际没有（别人的 `movk` 被算进来）

而且 `ncg_xor_key` **本体里 `movk lsl#48` 是 0 处** —— 它在 VM 解释器的
子函数里。所以连"在本体里找这条指令"都是错的。

##### 混淆器自己的日志才是最直接的一手证据

被跳过时 Amice 只打 debug 日志，不看就永远不知道：

```bash
RUST_LOG=amice=debug ./scripts/make-zip-lib.sh <ver> 2>&1 | grep -i 'skip function'
#   skip function "ncg_xor_key": function has non-call address uses
```

这条日志的成因见 4.3.4 ①：`annotate` 把函数地址写进
`@llvm.global.annotations`，VMP 判定"有非调用地址引用"就跳过。
拆成独立文件 + 文件级 `AMICE_VM_VIRTUALIZE` 才绕开。

#### 4.3.6 混淆改变了什么、没改变什么

**实测对比（`ncg_boot_key` 的 HKDF 调用点）**

VMP/FLA 之前：
```asm
adrp x4, 0xc000
add  x4, x4, #0x7d4     ← 指向 "nc-boot-v1"
mov  w1, #0x24          ← 36 字节 ikm
mov  w3, #0x10          ← 16 字节 salt
mov  w5, #0xa           ← 10 字节 info
mov  w7, #0x10          ← 16 字节输出
bl   khkdf_sha256       ← 直接调用
```

MBA 之后：
```asm
fmov d0, x9
fsub d0, d0, d1         ← 用浮点寄存器做整数减法（MBA 变形）
eor  w10, w21, w8
and  w11, w11, #0x1ffff
fadd d0, d1, d0
fmov x10, d0
```

**改变了的**：算式变复杂，读懂需要化简。

**没改变的（这三条是"认出算法"的捷径）**：

| 泄露点 | 位置 | 为什么改不掉 |
|---|---|---|
| `nc-boot-v1` 字符串明文 | `.rodata` | 是数据不是字面量，`make-sig-log.py` 的标记扫描扫不到 |
| HKDF 参数 `mov w1,#0x24` 等 | 函数体 | **函数调用参数**，混淆器改不了 ABI 约定 |
| FLA 状态码明文 `mov w8,#0x8937` | 函数开头集中 | `flatten_mode=basic` 就这样 |

**结论**：MBA+FLA 把"读懂"从 5 分钟抬到 1~2 小时，但**"认出是 HKDF"仍是 5 秒**。
要到"读不懂"，只有 VMP。

#### 4.3.7 实测强度对比

同一个 `ncg_xor_key`（源码 8 行）：

| 状态 | `ncg_xor_key` 指令数 | `.o` 体积 | VM 子段 | AI 能读懂吗 |
|---|---|---|---|---|
| 无混淆 `-Oz` | 15 | 1280 B | 0 | 立即 |
| MBA+FLA | 210（文档记录，未复测） | ~2 KB | 0 | 1 小时（化简 MBA） |
| **VMP** | **31** | **22720 B** | **14** | **读不懂**（要逆 VM 指令集） |

⚠️ **看这一列要小心**：VMP 的 `31` 比 MBA+FLA 的 `210` 小 7 倍，
只比无混淆的 `15` 多 16 条。VMP 的强度不体现在 `ncg_xor_key` 自己的
指令数上 —— 它把这个函数编译成 **VM 字节码**（在 `.rodata` 里，
5020 B），本体只剩"准备参数 + `bl 解释器`"。真正的实现搬到了
`.text` 里的解释器（8360 B）和另外 12 个 VM 子段中。

所以：**判断 VMP 是否生效看 VM 子段数（4.3.5），不要看指令数。**

## 5. 已知限制（不要当 bug 修）

| 项 | 现状 | 为什么不能/不值得修 |
|---|---|---|
| `.ncx` 等 6 个段名自解释 | `readelf -S` 一眼看出结构 | 改名要动契约头 + 26 处字面量 + 全部测试，收益只是"降低可发现性" |

| FLA 的状态码是明文常量 | `mov w8,#0x8937` 集中在函数开头 | `basic` 模式就这样；换 `dominator` 可能好些但未验证 |
| libc++ 5 条 `.rodata` 路径 | 删不掉 | 删了 `__cxa_demangle` 会崩 |

## 6. 排查速查

| 现象 | 先查 |
|---|---|
| 加密段塌成一个 | 静态库链接少了 `-Wl,--whole-archive` |
| `.ncx` 熵值 5.x（像明文） | 三步锁箱合并传参了，一级加密被跳过 |
| dlopen 即 SIGSEGV | `--strip-meta` 在 `--lock-head` 之前跑了 |
| 正常包也解不开（-12） | APK 证书读不到 / 包名对不上 |
| 改一位密文就崩但**没有** `-11` | 槽完整性检查被绕过（`sh_size` 改小了） |
| VMP 后指令数反而变少 | 被静默跳过，跑 `vmp-diag` job 看 Amice 决策 |
| `test.sh` 红 V6/V7 报 NOOPEN | 新增 `.c` 文件没同步四处清单 |
| VM 子段数报 0 | `vmp-diag` 的编译参数漏了 `-ffunction-sections -fdata-sections` |

### 消费方（artifact-pipeline）侧的排查

| 现象 | 先查 |
|---|---|
| 回编报 `Unsigned short value out of range: 65536` | **不要看报错类名**（随机的）。查 `dex-rebalance.py --check --apk <apk>`，看是 method 还是 field 贴顶 |
| 同上，且已做 dex 拆分仍报 | 拆分的容量算法是否三池都控（method/type/field 独立，上限都是 65536）|
| dcc 报 `'NoneType' object has no attribute 'class_def'` | 某个 dex 的 magic 是 038/039（androguard 只认 035~037），已修（`Dex2C` a1a517c），若复发查 `tools/dex2c.zip` 是否重打过 |
| nox 版本没跟着上游换 | `cat tools/nox/VERSION`；重跑 `make-zip-lib.sh` 后删旧的 `tools/nox/`（`.gitignore` 里的解压缓存）|
| `trigger_build.py` 出的包用着用着闪退 | 先抓 `adb logcat -b all \| grep -E 'nc:\|RT: m:'`：`RT: m: 0x4` = App 自己的 SupportGuard；`nc:` + SIGABRT = 我们的 env_check；`exited cleanly (0)` = `System.exit` 主动退 |
