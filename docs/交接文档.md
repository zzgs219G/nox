## 0.5 没有 Amice 怎么办（接手最先确认的事）

**结论：没有 Amice 也能完整开发、测试、发版。混淆是可选项，不是依赖。**

上手前先跑这条，确认你的环境是通的：

```bash
./test.sh                                    # 期望 23 通过（判据 0 失败）
ANDROID_NDK_HOME=/path/to/ndk \
  ./scripts/make-zip-lib.sh test-check       # 期望输出「未设 AMICE_BUNDLE，普通编译（无混淆）」
```

两条都过 = 你可以正常工作。**不需要** Rust / LLVM SDK / 预编译插件。

### 什么需要 Amice，什么不需要

| 操作 | 需要 Amice 吗 |
|---|---|
| 读代码、改代码 | ❌ |
| `./test.sh`（21 项） | ❌ |
| 普通版发版（`make-zip-lib.sh` / `make-zip-src.sh`） | ❌ |
| 锁箱（`so-section-lock.py` 三步） | ❌ |
| `nox protect` / `nox build` | ❌ |
| **混淆版发版**（带 `AMICE_BUNDLE=...`） | ✅ |

### 想要混淆版但没有 bundle

三个选项，按成本排序：

| 选项 | 做法 | 代价 |
|---|---|---|
| **① 不混淆** | 直接发普通版。功能完全相同，只是少了混淆 | 0 |
| **② 拿现成的** | 从 CI 的 release artifact 下载已混淆的包（`nox-v*-obf*.zip`） | 0 |
| **③ 自己下 bundle** | `amice-android-ndk-r29-linux-x86_64.tar.gz`（848MB，GitHub release） | 848MB 磁盘 |

⚠️ **bundle 与本仓库没有 git 关联**，它不进版本库，也不需要。它只是
编译时的工具，和 NDK 一个性质。

### 为什么混淆做在发布时而不是消费方

`libnox.a` 是已编译的机器码。Amice 是编译期 LLVM pass，只能在**编译源码**
时生效。消费方拿到 `.a` 之后无法再混淆其中函数 —— 这一点实测过：
消费方开 `AMICE_MBA=true` 后，`ncg_boot_key` 的反汇编与无混淆版逐条一致。

所以混淆必须在本仓库发版时固化进 `.a`。这也解释了为什么"没有 Amice"
不影响任何开发工作 —— 它只在"发混淆版"这一个动作里用到。

## 1. 五条最重要的坑（按踩到的代价排序）

### ① 混淆/VMP 与 annotate 互斥 —— 而且失败是静默的

VMP 遇到 `annotate` 标记的函数会**跳过**，日志只有开 `RUST_LOG=amice=debug`
才看得到：

```
skip function "ncg_xor_key": function has non-call address uses
```

原因：annotate 把函数地址写进 `@llvm.global.annotations` 表。

**最坑的地方**：跳过之后产物"看起来正常"。2026-11-06 一度以为
指令数变少说明"VMP 优化得好"，实际是被跳过了、退回原始编译。

**判据（2026-11-06 复核修正）**：看目标文件里有没有 **VM 子段**，
不要看指令数 ——

```bash
cd /tmp && ar x <nox>/so-guard/lib/arm64-v8a/libnox.a
readelf -SW nc_guard_xor.o | grep -c 'L\.L__'
#   14 行 → VMP 生效（.text..L.L__<hash> / .rodata..L.L__<hash> …）
#   0 行  → 没 VMP
```

**为什么不能看指令数**（本仓库实测）：

| 状态 | `ncg_xor_key` 指令数 | `.o` 体积 |
|---|---|---|
| 无混淆 `-Oz` | 15 | 1280 B |
| MBA+FLA | 210（文档记录，未复测） | ~2 KB |
| **VMP** | **31** | **22720 B** |

VMP 的 `31` 只比无混淆的 `15` 多 16 条，比 MBA+FLA 的 `210` 少 7 倍。
**"数字变小"判断不了任何事** —— 它可能是被跳过（→15），也可能是 VMP
把实现搬进了 VM 字节码（→31）。只有体积和 VM 子段数是单调的。

⛔ **也别在链接后的 `libnc.so` 上 grep** `sub sp,#0xc0` / `movk lsl #48`。
实测一个确认 VMP 的产物：这两条分别命中 9 处和 56 处，**全是无关代码** ——
`movk` 那 56 处第一处就是 APK 签名块 magic 常量（`"APK Sig "`/`"Block 42"`，
来自 `nc_guard_key.c`）。详见 `流程文档.md` 4.3.5。

### ② 三步锁箱是互斥分支，不能合并传参

```python
# so-section-lock.py 的真实逻辑
if args.strip_meta: return strip_meta(...)
if args.lock_head:  return lock_head(...)
return lock(...)          # ← 一级加密在这
```

传了 `--lock-head` 就**只**做二级锁箱。同时传 `--lock-head --strip-meta`
的结果是：`.ncx` 保持明文 ARM64 指令（熵 5.5），但日志会显示"已锁"。

**2026-11-05 CI 实测踩过这个**，症状是构建全绿、产物看起来正常。

### ③ 拆分/新增 `.c` 文件必须同步三处清单

```bash
grep -rn "nc_guard_boot.c" --include="*.sh" --include="*.yml" --include="nox" .
```

| 位置 | 漏了会怎样 |
|---|---|
| `test.sh` → `guard_compile()` | 链接缺符号，V6/V7 报 NOOPEN |
| `make-zip-lib.sh` → `LIB_SRCS` | 打包时漏编该文件 |
| `nox` → `GUARD_SRCS` | CLI 编译缺符号 |

2026-11-06 拆 `nc_guard_xor.c` 时三处全漏了，`test.sh` 立刻红 2 项。
这是"改一处必须 grep 所有消费方"的老教训（同 `AGENTS.md` 报错七）。

### ④ `-Wl,--whole-archive` 省不掉

`ncguard_unlock` 是 `constructor`，**没有任何代码显式引用它**。静态库默认按需
拉取 → 链接器判定"没人要" → 整个 `nc_guard_boot.o` 被丢弃 → 六个加密段塌成
一个。

实测：不加时 `.ncx/.ncxh/.nck/.ncks` 全消失，连 `unlock` 都找不到。

`--no-whole-archive` 必须紧跟其后收尾，否则 libc 也会被全量拉入。

### ⑤ VMP 的 `.o` 体积是单函数 20 倍

```
nc_guard_xor.o:  1-2KB（普通）→ 22720 字节（VMP）
libnox.a:        60858 → 81534 字节（+34%）
```

只对 1 个函数开就涨这么多。**别对整个文件开**（`AMICE_VM_VIRTUALIZE` 是
文件级/编译单元级开关，不是函数级）。

## 2. 解锁链是什么（改代码前必须理解）

```
constructor(50) ncg_boot_init
  └→ ncguard_unlock()                    明文 .text，调度
       ├→ ncg_slot_read()      读 .ncks 原始字节
       ├→ ncg_boot_key()       ★ CRC32(.text) + HKDF → boot_key
       ├→ ncg_rc4(boot_key)    解一级密钥槽 .nck
       ├→ ncg_xor_key()        ★ 碎片重组 → XOR_KEY
       ├→ ncg_stub_recover()   ★ 拼 k_stub + 验 MAC + 解 .ncxh
       └→ ncg_head_unlock()    .ncxh 密文，真正的密码学中控
            └→ 解 .ncx（业务代码）
```

**★ 标记的三个函数是攻击者唯一入口**（"造钥匙的配方"）。混淆/VMP 只作用于它们。

其余函数不需要保护：
- `ncg_rc4`/`khmac_sha256` —— 标准公开算法，混淆等于给公开算法加密码
- `ncg_slot_read`/`ncg_find_section`/`ncg_elf_*` —— 读文件字节、解析 ELF 头
- `ncg_head_unlock` —— **已在 `.ncxh` 密文段**，混淆多余（密文强得多）

### 两个时序约束（改了会死锁/崩）

1. **stub 只能调 `.text` 里的函数**。`ncg_stub_recover` 在 `.ncxh` 还没解开时
   就要工作，调 `.ncxh` 里的函数 = 执行密文 = SIGILL。
2. **`constructor(50)` 不能变**。`ncguard_unlock` 必须在 `sig_check_entry`
   （默认 `constructor(65535)`）之前跑完，否则校验代码踩密文。

## 3. 真实的强度缺口（别以为已经防住了）

### 3.0 ⚠️ 先读这条：VMP 的收益边界（2026-11-06 实测修正）

本文档此前按"AI 能否读懂函数体"评估强度，**那个口径低估了攻击者**。

2026-11-06 实际动手解了一遍（`docs/so逆向文档/` 的零信息逆向报告 +
自己用 Python 重写），结论：

```
① CRC32(.text) → boot_key → 解 .ncks → k_stub   ← 全程纯静态，没碰 VMP
```

**攻击者根本不需要读 VMP 保护的函数。** 他读 `so-section-lock.py`
（明文 Python，40 行的 `_derive_boot_key`）就够了，然后照抄。

所以：**VMP 抬高了「读懂实现」的成本，抬不高「复现算法」的成本。**
详细分析见 `so防护架构.md` §10。

### 3.1 当前 VMP 覆盖（14 个函数，实测）

```
ncg_boot_key / ncg_xor_key / ncguard_stub_recover / ncguard_derive_kstub
ncguard_head_mac_ok / ncguard_head_decrypt / ncguard_headro_unlock
ncg_magic_ok / ncg_rd32 / ncg_ctr_xor
ncg_self_pkg / ncg_find_apk_path / ncg_pkg_fault
    全部 VMP（19~31 条包装指令），nc_guard_crypto.o = 235 个 VM 子段
```

`nc_guard_boot.c` 里剩下的 20 多个函数（ELF 解析、watchdog、I/O）**没上 VMP**，
因为它们不是"造钥匙的配方"，且整文件开会把 `open/pread/close` 也虚拟化。

### 3.2 仍然存在的三个泄露点

| 泄露点 | 状态 |
|---|---|
| `nc-boot-v1` 等 HKDF label 明文 | ✅ **已修**（v0.9.6，XOR 0x5A 整数表 + 运行期还原）|
| HKDF 参数是明文立即数（`mov w1,#0x24`）| ❌ 仍在。但 VMP 后函数体变字节码，这些立即数在 VM 字节码里，静态看不到 —— 除非逆 VM |
| FLA(basic) 状态码明文（`mov w8,#0x8937`）| ⚠️ 部分。VMP 的函数走 VM 分派，不走 FLA；但 `nc_guard_boot.c` 里未 VMP 的函数仍可能带 FLA 状态码 |

**关键**：这三条都属于"提高读懂成本"，而攻击者不需要读懂（见 3.0）。

### 3.3 真正能提升强度的方向

| 方向 | 效果 | 成本 |
|---|---|---|
| **让仓库私有** | VMP 立刻有意义（攻击者只有 .so，必须逆） | 零 |
| **常量每次构建随机**（salt/label/碎片）| 读了 Python 也复现不了 | 中，改锁箱器 |
| 服务化（上传 so，服务器加密返回）| 算法不进客户端 | 大，改架构 |
| 继续加 VMP 覆盖 | **边际收益已到顶**（14 个函数）| — |

**别再往 VMP 上加东西了。**

`nc_guard_boot.c` 刻意不进这份清单 —— 它还有 25+ 个无关函数

### 4.2 历史记录：原文说的"做不到"及实际解法

原文（已过期，保留供理解设计演进）：

> **`ncg_boot_key`** 依赖 `ncg_slot_read / ncg_stub_find_text / ncg_boot_crc32 /
> ncg_wipe / khkdf_sha256`，拆文件要连带这些辅助函数一起挪。
>
> **`ncg_stub_recover`** 依赖 `ncg_slot_read / ncg_ctr_xor / ncg_rd32 / ncg_wipe /
> khmac_sha256 / dladdr / mprotect`，约 138 行，且**有时序约束**：先验 MAC 再解密、
> 用后即毁。VMP 引入的额外栈操作（`sub sp, sp, #0xc0`）可能影响它假设的栈布局。
>
> **两者都不能带 annotate**。

**实际解法**（三条，都是 2026-11-06 做的）：

1. **不用 annotate，改文件级开关** —— annotate 会把函数地址写进
   `@llvm.global.annotations`，Amice 判定 `has non-call address uses` 并静默跳过。
   解法是把函数拆到独立 `.c`，用 `AMICE_VM_VIRTUALIZE=true` 整文件开。
   （见 `nc_guard_crypto.c` 文件头）
2. **依赖不必一起挪** —— `ncg_boot_key` 依赖的辅助函数留在 `nc_guard_boot.c`，
   通过 `nc_guard_internal.h` 声明跨编译单元调用。它们不需要 VMP（通用 ELF 读取
   逻辑没有"配方"价值）。
3. **寄存器预算靠拆分解决** —— `ncguard_stub_recover` 被**拆了四次**
   （`ncguard_derive_kstub` / `ncguard_head_mac_ok` / `ncguard_head_decrypt` /
   `ncguard_headro_unlock`），把单函数基本块数从 16 降到个位数才过 VM 预算。
   所有拆出的函数必须加 `noinline`，否则 `-Oz` 会内联回去，拆分失效。

### 4.3 还剩什么没上 VMP（这才是真实缺口）

| 文件 | 函数数 | 为什么不上 |
|---|---|---|
| `nc_guard_boot.c` | 25+ | 含重型 I/O，整文件开体积暴涨；且都不是"造钥匙的配方" |
| `nc_guard_key.c` | SHA256/HMAC/HKDF | 标准公开算法，混淆等于给公开算法加密码 |
| `nc_guard_paths.c` | 2 条路径密文表 | 只是两条 `/proc` 路径 |
| `nc_guard_probe.c` | 段定义 | 只有 `ncguard_probe` 一个样例函数 |
| `nc_guard_jni.c` | JNI 入口 | 只调 `ncguard_unlock` + `ncguard_probe` |

⚠️ **但注意 `so防护架构.md §10` 的结论**：VMP 抬高了"读懂实现"的成本，
抬不高"复现算法"的成本 —— 因为 `so-section-lock.py` 是明文 Python，
攻击者读 40 行 `_derive_boot_key()` 就能复现，一次都不用碰 VMP。
所以"还剩什么没上 VMP"这个问题，**在仓库公开的前提下收益很有限**。

## 6. 版本与分发纪律

### 消费方怎么用

```
artifact-pipeline/tools/nox.zip    ← 本仓库 dist/nox-<ver>.zip 原样
```

换版后**必须删 `artifact-pipeline/tools/nox/`**（解压缓存，幂等靠
`nc_guard_layout.h` 存在判断）。

### 发版必做

```bash
# 打 tag（CI 会跑 test.sh + 打包 + 发布）
git tag -a v0.x.y -m "..." && git push origin v0.x.y
```

tag message 里要写**破坏性变更**（消费方需要知道）。例：
```
v0.5.0 selftest 符号改名 Java_com_nc_link_NcLink_selftest → nc_link_jni_selftest
```

### 混淆版单独标注

## 8. 一句话交接

**这套东西的强度来自"锁"（RC4+HMAC 六段加密、证书绑定密钥），不是"藏"。**
混淆和 VMP 只是把"读懂代码"的门槛抬高，改变不了这个本质。

改任何东西之前先问：**我会不会让某个历史产物再也解不开？**（`nc_guard_layout.h`
的任何改动都会）。如果不确定，先在 `./test.sh` 里加一条断言。
