## 1. 五条最重要的坑（按踩到的代价排序）

### ① 混淆/VMP 与 annotate 互斥 —— 而且失败是静默的

VMP 遇到 `annotate` 标记的函数会**跳过**，日志只有开 `RUST_LOG=amice=debug`
才看得到：

```
skip function "ncg_xor_key": function has non-call address uses
```

原因：annotate 把函数地址写进 `@llvm.global.annotations` 表。

**最坑的地方**：跳过之后产物"看起来正常"，但指令数会**大幅减少**
（`ncg_xor_key` 从 210 条降到 15 条）。2026-11-06 我一度以为
"指令数少了说明 VMP 优化得好"，实际是被跳过了、退回原始编译。

**判据**：VMP 生效 → 指令数涨到数百 + 出现 `movk ..., lsl #48`；
被跳过 → 指令数降到十几条。

### ② 三步锁箱是互斥分支，不能合并传参

```python
# so-section-lock.py 的真实逻辑
if args.strip_meta: return strip_meta(...)
if args.lock_head:  return lock_head(...)
return lock(...)          # ← 一级加密在这
```

传了 `--lock-head` 就**只**做二级锁箱。同时传 `--lock-head --strip-meta`
的结果是：`.ncx` 保持明文 ARM64 指令（熵 5.5），但日志会显示"已锁"。

**2026-11-05 CI 实测踩过这个**，症状是构建全绿、产物看起来正常。

### ③ 拆分/新增 `.c` 文件必须同步三处清单

```bash
grep -rn "nc_guard_boot.c" --include="*.sh" --include="*.yml" --include="nox" .
```

| 位置 | 漏了会怎样 |
|---|---|
| `test.sh` → `guard_compile()` | 链接缺符号，V6/V7 报 NOOPEN |
| `make-zip-lib.sh` → `LIB_SRCS` | 打包时漏编该文件 |
| `nox` → `GUARD_SRCS` | CLI 编译缺符号 |

2026-11-06 拆 `nc_guard_xor.c` 时三处全漏了，`test.sh` 立刻红 2 项。
这是"改一处必须 grep 所有消费方"的老教训（同 `AGENTS.md` 报错七）。

### ④ `-Wl,--whole-archive` 省不掉

`ncguard_unlock` 是 `constructor`，**没有任何代码显式引用它**。静态库默认按需
拉取 → 链接器判定"没人要" → 整个 `nc_guard_boot.o` 被丢弃 → 六个加密段塌成
一个。

实测：不加时 `.ncx/.ncxh/.nck/.ncks` 全消失，连 `unlock` 都找不到。

`--no-whole-archive` 必须紧跟其后收尾，否则 libc 也会被全量拉入。

### ⑤ VMP 的 `.o` 体积是单函数 20 倍

```
nc_guard_xor.o:  1-2KB（普通）→ 22720 字节（VMP）
libnox.a:        60858 → 81534 字节（+34%）
```

只对 1 个函数开就涨这么多。**别对整个文件开**（`AMICE_VM_VIRTUALIZE` 是
文件级/编译单元级开关，不是函数级）。

## 2. 解锁链是什么（改代码前必须理解）

```
constructor(50) ncg_boot_init
  └→ ncguard_unlock()                    明文 .text，调度
       ├→ ncg_slot_read()      读 .ncks 原始字节
       ├→ ncg_boot_key()       ★ CRC32(.text) + HKDF → boot_key
       ├→ ncg_rc4(boot_key)    解一级密钥槽 .nck
       ├→ ncg_xor_key()        ★ 碎片重组 → XOR_KEY
       ├→ ncg_stub_recover()   ★ 拼 k_stub + 验 MAC + 解 .ncxh
       └→ ncg_head_unlock()    .ncxh 密文，真正的密码学中控
            └→ 解 .ncx（业务代码）
```

**★ 标记的三个函数是攻击者唯一入口**（"造钥匙的配方"）。混淆/VMP 只作用于它们。

其余函数不需要保护：
- `ncg_rc4`/`khmac_sha256` —— 标准公开算法，混淆等于给公开算法加密码
- `ncg_slot_read`/`ncg_find_section`/`ncg_elf_*` —— 读文件字节、解析 ELF 头
- `ncg_head_unlock` —— **已在 `.ncxh` 密文段**，混淆多余（密文强得多）

### 两个时序约束（改了会死锁/崩）

1. **stub 只能调 `.text` 里的函数**。`ncg_stub_recover` 在 `.ncxh` 还没解开时
   就要工作，调 `.ncxh` 里的函数 = 执行密文 = SIGILL。
2. **`constructor(50)` 不能变**。`ncguard_unlock` 必须在 `sig_check_entry`
   （默认 `constructor(65535)`）之前跑完，否则校验代码踩密文。

## 3. 三个真实的强度缺口（别以为已经防住了）

按"AI 能否读懂"评估，当前状态：

| 函数 | 保护 | AI 能读懂吗 |
|---|---|---|
| `ncg_xor_key` | **VMP** | ❌ 读不懂（只能看到 VM 帧 + 3 个 64 位常量 + `bl`） |
| `ncg_boot_key` | MBA+FLA | ⚠️ 能，约 1~2 小时化简 |
| `ncg_stub_recover` | MBA+FLA | ⚠️ 能，同上 |

**攻击者会挑最弱的那个下手。** 整体强度受限于后两个。

### 三个已实测的泄露点

1. **`nc-boot-v1` 等 HKDF label 明文在 `.rodata`** → `xref` 一下定位到函数
2. **HKDF 参数是明文立即数**（`mov w1,#0x24` = 36 字节 ikm）→ 看参数就认出算法
3. **FLA(basic) 的状态码是明文常量**（`mov w8,#0x8937` 集中在函数开头）→ 按状态
   码跟踪跳转即可还原 CFG

这三条不解决，加再多 pass 也只是让"还原"从 5 分钟变 20 分钟。

### 继续加强的三条路（成本递增）

| 路线 | 效果 | 成本 |
|---|---|---|
| 把 `ncg_boot_key`/`ncg_stub_recover` 也拆文件 + VMP | 3 个函数全覆盖 | 依赖重（见 §4），`ncg_stub_recover` 有时序风险 |
| 藏锚点（字符串运行期拼装、参数运行期计算） | 去掉"认算法"的捷径 | 改业务代码，不影响混淆 |
| 换 `flatten_mode=dominator` | 状态码可能被加密 | 一行改动，未验证 |

## 4. 如果要继续给另外两个函数上 VMP

它们现在做不到的三个原因（都实测过）：

**`ncg_boot_key`** 依赖：
```
ncg_slot_read / ncg_stub_find_text / ncg_boot_crc32 / ncg_wipe / khkdf_sha256
```
拆文件要连带这些辅助函数一起挪。

**`ncg_stub_recover`** 依赖：
```
ncg_slot_read / ncg_ctr_xor / ncg_rd32 / ncg_wipe / khmac_sha256 / dladdr / mprotect
```
约 138 行，且**有时序约束**：先验 MAC 再解密、用后即毁。VMP 引入的额外栈操作
（`sub sp, sp, #0xc0`）可能影响它假设的栈布局。

**两者都不能带 annotate**（§1 ①）。

## 5. 验证的真实边界

| 能验 | 在哪验 |
|---|---|
| 编译、段表、熵值、`.dynsym`、strip 效果 | ✅ CI（x86_64 静态检查） |
| `test.sh` 的 V1/V2/V3/V4/V8 | ✅ CI（源码形态，任何架构都行） |
| `test.sh` 的 V5/V6/V7/V9 | ✅ CI（源码形态）/ ⏭ `.a` 形态跳过 |
| **`.a` 形态产物的 `dlopen` 解锁** | ⚠️ **只有真机能验**（ARM 产物，x86 宿主跑不了） |
| 混淆/VMP 后的真机可运行性 | ⚠️ **只有真机能验** |

⚠️ **V5/V6/V7/V9 跳不跳，判据是 `CAN_EXEC`，不是宿主架构**：
`test.sh:116` 是 `CAN_EXEC=1 当且仅当有源码`。源码形态编出来的是**本机
架构**产物，在 aarch64 Termux 上照样真跑（实测 21 通过）；只有静态库
形态（`HAS_SRC=0`，`.a` 是 ARM）才 `CAN_EXEC=0`。所以"CI 在 x86 上跑
ARM 产物"这个说法只对 `.a` 形态成立 —— 而发布环节的冒烟测试恰好解压
的就是 `.a` 形态的包。

**这是最大的验证缺口**：VMP 生成代码最容易在真机崩（VM 帧、寄存器映射、边界），
而 CI 全绿也说明不了什么。

真机验证判据：
```bash
adb logcat | grep -E "nc *:|selftest"
# 期望看到：so 已加载 → 环境检测通过 → 指纹比对一致,放行
# selftest 应返回 59（无 "selftest rc=..." 警告即正常）
```

## 6. 版本与分发纪律

### 消费方怎么用

```
artifact-pipeline/tools/nox.zip    ← 本仓库 dist/nox-<ver>.zip 原样
```

换版后**必须删 `artifact-pipeline/tools/nox/`**（解压缓存，幂等靠
`nc_guard_layout.h` 存在判断）。

### 发版必做

```bash
# 打 tag（CI 会跑 test.sh + 打包 + 发布）
git tag -a v0.x.y -m "..." && git push origin v0.x.y
```

tag message 里要写**破坏性变更**（消费方需要知道）。例：
```
v0.5.0 selftest 符号改名 Java_com_nc_link_NcLink_selftest → nc_link_jni_selftest
```

### 混淆版单独标注

混淆/非混淆产物的 `.a` 大小差 30%+，消费方调不了任何参数（混淆已固化）。
所以**版本号里带标记**：`v0.9.0-xorvmp`。

## 8. 一句话交接

**这套东西的强度来自"锁"（RC4+HMAC 六段加密、证书绑定密钥），不是"藏"。**
混淆和 VMP 只是把"读懂代码"的门槛抬高，改变不了这个本质。

改任何东西之前先问：**我会不会让某个历史产物再也解不开？**（`nc_guard_layout.h`
的任何改动都会）。如果不确定，先在 `./test.sh` 里加一条断言。
