## mprotect-粒度与同页可写段

**症状**：dlopen 阶段直接 SIGSEGV，崩溃点在 `.bss` 或相邻数据段，
tombstone 显示 `SEGV_MAPERR` / `SEGV_ACCERR`，完全没有指向 mprotect。

**根因**：`mprotect` 的粒度是【页】（4KB），不是段。
若把某段设成只读，而同页还有 `.bss` / `.data`，那些段也会变只读
→ 之后任何写入即 SIGSEGV。

**实测布局**：`.ncxr`（17B）与 `.bss`（9968B）同页 → 给 `.ncxr` 设
`PROT_READ` 会把整页（含 `.bss`）变只读。

**修法**：`ncg_page_has_writable_neighbor()` —— 判据是
「覆盖该段的整页范围内，有没有 `SHF_WRITE` 的段」，不是「这段是不是数据」。
有则保持 `RW`。

**本项目踩过三次**（`.ncxr`/`.bss`、`.ncxhr`/`.bss`、报告缓冲撑大 `.bss`）。
**纪律**：本设施里【任何新增全局变量】都要先确认 `.bss` 没跨页。

## xor_key-碎片化

**背景**：8 字节 `XOR_KEY` 原是一整串常量放在 `.rodata`，
HEX 搜索直接命中（实测 `7e31a50dc8924bf6` 在 so 里明文出现 2 次）。

**现行机制**（2026-10-21 起）：
- 真碎片在 slot 碎片区 `NC_OFF_FRAGS[104:112)`，锁箱器每次构建随机生成
- `ncg_frag_a/b/c/d` 是【诱饵】：随机初值 + 参与假运算 + 防 gc-sections
  回收。攻击者对 `.data` 拼出的是随机值。兼作 diff 掩护
  （每次构建都在，看起来仍像老机制）
- `NCG_XOR_FRAG` 查表在 `.rodata` 无妨 —— 没有真碎片，表只是排列规则

**两条实测证伪的旧方案（别退回）**：

1. **4 个 `uint16` 各放一个 `noinline static` 函数** —— 无效。
   LLVM 做跨函数常量传播，把完整 8 字节密钥折回 `.rodata`
   （实测 boot.o `0x5b0`/`0x5b8`）。只有 `volatile` 这类标准级屏障才真阻止折叠。
2. **碎片放 `.data` 常量** —— 无效。破解复盘实测「`objdump` 读 `.data` +
   反汇编 5 分钟重组出 `XOR_KEY`」。真碎片必须来自构建期随机。

**⚠️ 2026-10-22 删掉一条【从未成立】的"反向纪律"**：

原文宣称「key16 中间值经栈偏移 `[sp+0x40]` 在函数间隐式传递，IDA/r2 追不到源，
这层白捡的防御是 `-Oz` 栈分配的副产品」。核实后有两处问题：

1. **归因错**：破解复盘报告说的 `[sp+0x40]` 是 `ncg_head_unlock` 里
   `pread(fd, slotdata, 96, slot.sh_offset)` 的 offset 参数 —— 那是
   `Elf64_Shdr` 结构体跨函数传递落在栈上的字段，属正常编译产物，
   不是"刻意设计的隐式传参"。报告作者把它误读成混淆手法，注释又把误读当事实。
2. **现象已不存在**：实测当前产物（`-Oz`）`ncg_xor_key` 是【孤立函数】
   （`nm` 可见独立符号，`ncguard_unlock` 内对它 `bl` 调用 = 0 次，
   所有调用点都被内联），不存在"跨帧栈槽传递密钥"。

**为什么不试图恢复它**：它依赖 `-Oz` 的栈分配决策，编译器一升级就可能变；
而源码注释一旦宣称"我们有这层防御"，后续所有加固判断都会建立在错误前提上。
**不可维护的防御不该写进注释当保障。**

**真正强的防线是 CRC 自绑定**（见 `ncg_self_crc`）：改 `.text` 任一字节 →
CRC 变 → `k_stub` 变 → `.ncxh` 解出垃圾 → SIGILL。破解复盘 v2 做了对照实验
证实（改一条正常运行 100% 不可达的指令仍 SIGILL），且它试图绕过
（重加密 `.ncxh`）仍失败 —— 因为它漏了 `.ncxhr` 也依赖 `k_stub`。
那条靠的是链式依赖，不是误导。

## 反多开-路径白名单

**威胁模型**：攻击者把 App 装进「应用双开 / 虚拟空间」里跑。
- 双开（MIUI/EMUI/ColorOS 的「应用分身」）：`/data/user/<uid>/pkg/`
- 虚拟空间（VirtualXposed / 太极 / 平行空间）：`/data/data/<宿主>/virtual/`

那里：
- 包名与主环境【完全相同】→ `ncg_pkg_fault` 的包名指纹校验照样通过
- 调试器/hook 框架可随意 attach 而不污染主环境
- 攻击者可「改一处 → 跑一次」反复试错，主环境零痕迹

**即：包名绑定挡不住「同一个包名的另一个实例」。**

**与 Epic 的刻意差异**：Epic 用 `pause()` 硬拒。实测中国 ROM 的「应用双开」
走 `/data/user/<uid>/`，硬拒会让**所有双开用户直接闪退** —— 那是产品事故，
不是安全收益。

**本实现的取法：不做判定点，只污染密钥**（与 `ncg_pkg_fault` 同一思路）。
调用方没有 `if`，攻击者无法「把某个判断改成 `return 1`」绕过。
要绕过必须【同时】伪造路径与包名，且伪造结果要能算出正确的 `k_so` ——
而 `k_so` 的输入含证书 DER，他不知道。

**白名单**（实测覆盖 Play / 国内商店 / ADB 安装）：
`/data/app/`、`/mnt/expand/`、`/data/user_de/`

**黑名单**：`/data/user/`（双开）、`/data/data/`（虚拟空间）、
`/data/local/tmp/`（手动 push）

**⚠️ 路径字面量不落明文**：走 `ncg_path_s` 密文表会牵动 `gen-paths.py`
与布局契约（新增 ID 要同步 Python 侧），收益不抵风险。改用
「首字节 + 长度」的轻量比对，字符串在 `.rodata` 里是分段常量，
`strings` 扫不到完整路径（实测见 commit message）。
**这是【混淆】不是【加密】** —— 如实标注，别高估。

## 槽完整性-fail-open-修复

**原实现**（2026-10-28 前）：

```c
int have_mac = (got >= 96) && (slot.sh_size >= 96);
if (have_mac) { 验 HMAC }     // ← 把 .nck 段表 sh_size 改小即整块跳过校验
```

而 `sh_size` 不在 `crc32(.text)` 覆盖范围、也不在任何 MAC 里 → 改它零成本。

**实测四变体**：
- A 原样 → `selftest=59`
- **B 只改 `sh_size`→0 → 得 59（放行，漏洞）**
- C 只篡改 → `-11`（MAC 有效）
- **D 关 MAC + 篡改 → 137（篡改生效）**

**修法**：magic 判"未锁"在前、之后槽不完整直接 `-11`、MAC 校验无开关。
修复后 B/D 均 `-11`。

## 解密后明文完整性基线

**动机**：解锁成功后 `.ncx` 明文常驻文件映射页，此后【再无任何自检】。
Frida 的 `Interceptor` 默认走 inline hook —— 必然改写该页指令，
而实现对"代码被改"完全无感知、不报错、不处置。

**为什么必须在解密完成那一刻采集基线**：攻击者可以在 unlock 返回后、
watchdog 首次轮询前挂 hook。若基线在 hook 之后才采，就把"已被 hook 的版本"
当成正确基线，检测永久失效。

**为什么能这样比**（前提已实测）：`.ncx` 段【零重定位】——
实测 365 个重定位全部落在 `0x12310` 之后，而 `.ncx` 结束于 `0xded4`。
故文件字节 == 内存字节，运行期内存 CRC 与构建期一致，可直接以
"解锁后内存快照"作基线自比（不依赖文件读取，零 I/O）。

## 代码自绑定-k_stub

**动机**：抗静态 patch。此前 `k_stub` 与代码零关联，攻击者 patch 明文 stub
（如把 HMAC 校验改恒真）无需代价。

**机制**：

```
cipher_key = k_stub ^ fold(crc32(.text))
```

运行期 stub 先对 `.text` 算同样的 CRC，异或回去才能得到正确密钥。
改任何一处明文代码 → CRC 变 → 密钥错 → head 解出乱码 → SIGILL。

**为什么能自洽**：`.text` 段 `addr == offset` 且整体无重定位
（实测 `readelf -r` 的重定位全部落在 `0x71d0` 之后，`.text` 结束于 `0x2714`），
所以锁箱期按文件算的 CRC == 运行期按内存算的 CRC。

**注意**：CRC 覆盖 `.text`【锁箱前】的字节；二级锁箱只改 `.ncxh`，
不动 `.text`，所以运行期看到的 `.text` 与锁箱期完全一致。

## sha256-ctr-替代周期-xor

**原实现**（2026-10-30 前）：16 字节周期 XOR（`cipher[i] = plain[i] ^ k[i & 15]`）。

**为什么必须换**：周期 XOR 是本仓库唯一的密码学硬伤
- 攻击者对密文做间隔 16 的自相关即可看出周期 → 恢复 `k_stub_eff`
- 周期 XOR 只能提供"混淆"，提供不了"抗已知明文"
- ARM64 函数序言高度可猜 → 已知明文攻击直接成立

**现实现**：`SHA-256-CTR`，`keystream[i] = SHA256(key || dom || LE32(counter))`。

**为什么不用 RC4**：stub 侧（`.text` 明文）不能出现 256 字节 S 盒初始化循环
—— 那是"这是 RC4"的活招牌，且会撑大攻击者唯一能直读的 stub。
而 SHA-256 已在 `.text` 明文段可用（`nc_guard_key.c` 的 `ksha256`），
stub 已在用它验 head MAC → 零新增依赖。

**⚠️ 域分隔**：`CTR_DOM_HEAD=0x01`、`CTR_DOM_HEADRO=0x02`。
搞错域 → 解出乱码。head 与 master 共用同一把 `k_stub_eff`，
若都从 `counter=0` 起就构成 two-time-pad。

## 用后即毁-边界

**攻击面**：stub XOR 解出 `.ncxh` 明文后，攻击者在 SIGILL handler 里抢 dump。
明文从解密起【直到进程死】一直驻留。

**现在只抹 master（32B）**：断掉"dump 全内存 → 离线重算 `k_so`"这条路。
攻击者 dump 到的是全零 master，有调度器代码也推不出密钥。

**⚠️ `.ncxh` 代码区【不抹】—— 两轮实测均 SIGSEGV**：
1. 在 `ncg_head_unlock` 尾部自抹：PC 在本段内执行时自毁 → 崩
2. 挪到 `.text` 侧（PC 已离开）仍崩：抹除 + `clear_cache` 会破坏 `.ncxh`
   段内的链接器常量池/veneer（ARM64 `ldr`-literal 池就在函数尾同 section），
   I-cache 失效后取指落在已毁数据。veneer 位置随链接器版本变，安全边距不可靠

**代价（如实）**：代码区驻留 = "逻辑可读但无密钥可用"（复盘报告的攻击者
正是卡在这一点），动态路径由 hook 探针 + anti-diff 继续把守。

**⚠️ 抹除必须在 `.text` 侧做**，不能放在 `ncg_head_unlock`（`.ncxh` 内）
—— 那里 PC 还在本段，自毁会取到半新半旧的指令流。

## elf32-elf64-统一抽象

**症状**：v7a 产物（ELF32）在 32 位设备上启动即 SIGILL。

**根因**：`nc_guard_boot.c` 三处 ELF 解析全硬编码 `Elf64_Ehdr`/`Elf64_Shdr`。
用 ELF64 结构读 ELF32 文件会得到
`e_shoff = 0x28000900200034`（真实 `0x335a8` —— 把 `e_phoff` + `e_shoff`
两个 32 位字段拼成一个 64 位读）→ `pread` 读回 0 字节 → `boot_key` 失败
→ `.ncx` 不解密 → SIGILL。

**现实现**：`ncg_elf_hdr` / `ncg_elf_shdr` 两个轻量抽象，
按 `e_ident[EI_CLASS]` 分派，产出统一的 `ncg_shdr_t`。

**三条纪律**：
1. 抽象必须放 `.text`（明文）—— `ncg_boot_key` 要在 `.ncxh` 尚未解密时
   就算出来，而 `.ncxh` 里的 `ncg_find_section` 也消费同一套函数。
   两边都调它，它自己不能在任何加密段，否则"用密文解密文"。
2. 不要放进 `nc_guard_layout.h` —— 那是常量契约文件，
   **零 include 零逻辑**是刻意约束（会被拷进各种 NDK 工程）。
3. **任何 ELF 解析改动必须双 ABI 验证**，不能只测 arm64。

## jni-符号隐藏的上限

**外部报告给"符号表处理"打 0.0 分**（`nm -D` 看到 `Java_xxx` 带地址与大小）。

**根因**：`lib-ndk.sh` 的整段 version script 被包在
`if [ -f "$jni/nc_jni_gen.c" ]` 里，而该文件的生成器已在 `a7d9cbc`
（动态注册真机崩，回退短名绑定）连同 `nc_jni_register.c/.h` 一起删除
→ **condition 恒假 → version script 自 `a7d9cbc` 起从未生效过**。

`--strip-all` 只删 `.symtab/.strtab`，删不掉 `.dynsym`，补不上这个洞。

**修复**：拆掉 guard + 白名单 `Java_*` + 补 `-Wl,--undefined-version`。

**⚠️ 能力边界（如实）**：
- `-fvisibility=hidden` 本身已隐藏普通内部符号，version script 的**新增**
  收益只是挡住 `visibility("default")` 强行导出的运行时符号
  （实测挡住 `__clear_cache` / `__init_cpu_features` /
  `__init_cpu_features_resolver` 3 个）
- **「隐藏 JNI 符号」与「短名绑定」二者不可兼得** —— `Java_*` 无论加不加
  都必须在 `.dynsym`，业务方法名依旧可见
- 想真正隐藏只有动态注册，而动态注册在 so 加载时机（Application 初始化中）
  会崩（`a7d9cbc` 真机实证）

## 报告缓冲撑大-bss

**症状**：加了自检报告后，真机 SIGILL，pc 落在 `.ncx` 里，
寄存器全是垃圾值 —— 完全不指向"多了一个全局数组"。

**根因**：报告缓冲第一版用 `static char s_buf[4096]`，`.bss` 从 2,312B
涨到 3,864B，导致 `.ncxhr`（master，32B）与 `.bss` 的页面归属改变 →
`ncg_page_has_writable_neighbor()` 判定随之变 → SIGILL（rc=132）。

**修法**：缓冲放【栈上】，由调用方传入。报告约 1.2KB，栈完全承受得起。

**这是本项目第三次踩 `.bss` 同页坑。纪律见
[#mprotect-粒度与同页可写段](#mprotect-粒度与同页可写段)。**

## 段名重复导致双重加密

**症状**：真机 SIGILL，pc = `libnc.so+0x822c8`（`.ncx+0x8f78`），
`fault addr` 是垃圾。解锁前 `.ncx`/`.nct` 保持密文。

**根因**：`protect.sh` 的段列表用字符串拼接：

```bash
_SECTIONS=".ncx"
_SECTIONS=".nct,$_SECTIONS"          # → .nct,.ncx
_SECTIONS=".nct,.ncv,$_SECTIONS"     # → .nct,.ncv,.nct,.ncx  ← .nct 两次！
```

第二句已加入 `.nct`，第三句又写死一遍前缀。后果：
- `.nct` 被 RC4 加密两次 → **等于还原成明文**
- MAC 输入把 `.nct` 密文拼了两遍

**铁证**（用产物反算 MAC）：
```
旧段序 [.nct,.ncv,.nct,.ncx,.ncxr] → MAC 匹配 ✅（构建时用的就是这个）
正确序 [.nct,.ncv,.ncx,.ncxr]      → MAC 不匹配 ❌（运行期 nox 用的）
```

**修法（两层）**：
1. 改用数组 `_SEC_ARR+=()` —— 每个段只在 append 处出现一次，
   顺序由 append 决定，不可能重复
2. 加断言：`sort | uniq -d` 检查重复，有重复直接 `exit 1`

**教训**："同名段被处理两次"这类 bug 的症状**永远不指向真正原因** ——
RC4 两次 = 明文，MAC 拼两遍 = 校验失败，两者叠加后表现为"执行密文 SIGILL"，
看起来像解密没跑或钥匙错。

## 两套-vmp-段名必须不同

**症状**：真机 SIGSEGV，pc = `.ncr+0x5bc8`，
`x20=0x48416df089015220`、`x22=0x926fe538d8d6e746` 全是垃圾值。

**根因**：两套 VMP 用了相同的段名（`AMICE_VM_DATA_SECTION=".ncq,.ncs"`），
链接进同一个 so 后混在一起。`.ncs` 里 129 个 `R_AARCH64_RELATIVE` 重定位
的 addend **全部**指向 `.text`（那是第二套的 handler 表），第一套的表被挤掉/错位。
`.ncr` 里的第一套解释器按 `adr` 偏移去 `.ncs` 找自己的表 → 找到第二套的
→ VM 寄存器读到垃圾。

**修法**：段名按套分开
```
第一套：.ncq 字节码 / .ncs descriptor 表
第二套：.ncv 字节码 / .ncw descriptor 表
```

**教训**："两套看似独立的机制，如果共用某个全局命名空间，一定会在链接期冲突。"

## 单文件源清单漏改

**症状**：`dlopen` 报 `cannot locate symbol: ncg_report_flush`，
而 `boot.c` 明明引用了它。编译不报错。

**根因**：本项目有四处独立维护的 `.c` 清单：
1. `test.sh` 的 `guard_compile`
2. `make-zip-lib.sh` 的 `LIB_SRCS`
3. `nox` CLI 的 `_guard_sources()`
4. `protect.sh` 的拷贝清单

新增一个 `.c` 时漏改任一处，症状都是"分 TU 编译不报错（各 `.c` 各自编 `.o`
都成功），只在链接后 `dlopen` 才炸"，且报错只说 `undefined symbol: xxx`，
**不指向清单本身**。

**2026-11-13 一天内踩了四次。**

**修法**：
- `test.sh` 改通配符（排除 `nc_guard_jni.c` —— 它要 NDK 的 `jni.h`，
  宿主编译未必有）
- `make-zip-lib.sh` 的 `LIB_SRCS` 保留显式（生产清单，含 jni）
