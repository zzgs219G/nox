## K-01 mprotect 页粒度导致同页可写段变只读

| 项 | 内容 |
|---|---|
| **文件** | `nc_guard_boot.c`（`ncg_decrypt_one_seg` 段权限恢复） |
| **症状** | dlopen 阶段 SIGSEGV，崩溃点在 `.bss` 或相邻段。tombstone 显示 `SEGV_MAPERR` / `SEGV_ACCERR`，**完全不指向 mprotect** |
| **根因** | `mprotect` 粒度是页（4KB）不是段。把某段设只读时，同页的 `.bss`/`.data` 也变只读 → 之后任何写入即 SIGSEGV |
| **实测** | `.ncxr`（17B）与 `.bss`（9968B）同页 → 给 `.ncxr` 设 `PROT_READ` 把整页（含 `.bss`）变只读 |
| **修法** | `ncg_page_has_writable_neighbor()` —— 判据是「覆盖该段的整页范围内有没有 `SHF_WRITE` 的段」，不是「这段是不是数据」 |
| **复发次数** | **3 次**（`.ncxr`/`.bss`、`.ncxhr`/`.bss`、报告缓冲撑大 `.bss`，见 K-10） |
| **纪律** | 本设施里**任何新增全局变量**都要先确认 `.bss` 没跨页 |

## K-02 XOR_KEY 碎片化：两种藏法都无效

| 项 | 内容 |
|---|---|
| **文件** | `nc_guard_boot.c`（`ncg_xor_key`）+ `nc_guard_crypto.c` |
| **症状** | `strings` / HEX 搜索直接命中完整 8 字节密钥（实测 `7e31a50dc8924bf6` 出现 2 次） |
| **根因** | 原实现是 `.rodata` 里一整串常量 |
| **无效方案 ①** | 4 个 `uint16` 各放一个 `noinline static` 函数 —— LLVM 跨函数常量传播把完整密钥折回 `.rodata`（实测 boot.o `0x5b0`/`0x5b8`）。只有 `volatile` 这类标准级屏障才真阻止折叠 |
| **无效方案 ②** | 碎片放 `.data` 常量 —— 破解复盘实测「objdump 读 `.data` + 反汇编 5 分钟重组出 XOR_KEY」 |
| **现行修法** | 真碎片在 `slot[104:112)`，**构建期随机**；`ncg_frag_a/b/c/d` 是诱饵（随机初值 + 假运算 + 防 gc）；查表 `NCG_XOR_FRAG` 在 `.rodata` 无妨（没有真碎片，表只是排列规则） |
| **另一条** | `boot_key` 由 `.text` CRC + 首尾字节派生，加密两个槽段。攻击者拿到 so 后槽不再是明文表 |

## K-03 反多开：包名绑定挡不住同包名的另一个实例

| 项 | 内容 |
|---|---|
| **文件** | `nc_guard_boot.c`（`ncg_apk_path_fault`） |
| **威胁模型** | 双开 `/data/user/<uid>/`、虚拟空间 `/data/data/<宿主>/virtual/` 里包名与主环境**完全相同** → 包名指纹校验照样通过 |
| **与 Epic 的差异** | Epic 用 `pause()` 硬拒。实测中国 ROM 应用双开走 `/data/user/`，硬拒会让**所有双开用户闪退** —— 产品事故，不是安全收益 |
| **修法** | 不做判定点，只污染密钥：合法路径 → fault 全 0 → 密钥不变；异常路径 → fault 非 0 → `k_so` 污染 → MAC 失败 → fail-closed。**调用方没有 `if`，无法改成 `return 1` 绕过** |
| **白名单** | `/data/app/` `/mnt/expand/` `/data/user_de/` |
| **黑名单** | `/data/user/` `/data/data/` `/data/local/tmp/` |
| **强度边界** | 路径字面量用「首字节 + 长度」轻量比对，`strings` 扫不到完整路径。**这是混淆不是加密** |

## K-04 槽完整性 fail-open：改段表 sh_size 即跳过校验

| 项 | 内容 |
|---|---|
| **文件** | `nc_guard_boot.c`（`ncg_head_unlock` 的完整性校验）+ `so-section-lock.py` |
| **症状** | 篡改密文后 selftest 仍是 59（放行） |
| **根因** | `int have_mac = (got >= 96) && (slot.sh_size >= 96); if (have_mac) {验HMAC}` —— 把 `.nck` 段表 `sh_size` 改小即**整块跳过校验**。而 `sh_size` 不在 `crc32(.text)` 覆盖范围、也不在任何 MAC 里 → 改它零成本 |
| **实测四变体** | A 原样 → 59 / **B 只改 `sh_size`→0 → 59（放行，漏洞）** / C 只篡改 → -11（MAC 有效） / **D 关 MAC + 篡改 → 137（篡改生效）** |
| **修法** | magic 判"未锁"在前、之后槽不完整直接 `-11`、MAC 校验无开关。修复后 B/D 均 `-11` |
| **铁律** | magic 之后**不允许**再有"长度不够就放行"的分支 |
| **同类病** | 本仓库第三次（报错五十二 `lock_head` 段缺失 return 0、报错五十四 `env_mem_readable` 取不到就当通过） |

## K-05 ELF32/ELF64 混用：32 位设备启动即 SIGILL

| 项 | 内容 |
|---|---|
| **文件** | `nc_guard_boot.c`（`ncg_elf_hdr` / `ncg_elf_shdr`） |
| **症状** | v7a 产物在 32 位设备上启动即 SIGILL，崩溃点在 `.ncxh`（密文段），**完全不指向 ELF 解析** |
| **根因** | 解析硬编码 `Elf64_Ehdr`/`Elf64_Shdr`。用 ELF64 结构读 ELF32 文件得到 `e_shoff = 0x28000900200034`（真实 `0x335a8` —— 把 `e_phoff` + `e_shoff` 两个 32 位字段拼成一个 64 位读） |
| **连锁** | `pread` 读回 0 字节 → `boot_key` 失败 → `.ncx` 不解密 → 执行密文 → SIGILL |
| **修法** | `ncg_elf_hdr`/`ncg_elf_shdr` 按 `e_ident[EI_CLASS]` 分派，产出统一 `ncg_shdr_t` |
| **纪律 ①** | 抽象必须在 `.text`（明文）：`ncg_boot_key` 要在 `.ncxh` 未解时就算出来 |
| **纪律 ②** | 不放 `nc_guard_layout.h`（那是零 include 零逻辑的常量契约文件） |
| **纪律 ③** | **任何 ELF 解析改动必须双 ABI 验证** |

## K-06 两套 VMP 段名相同 → 链接后混淆

| 项 | 内容 |
|---|---|
| **文件** | `nc_guard_layout.h`（段名宏）+ `protect.sh`（`AMICE_VM_DATA_SECTION`） |
| **症状** | 真机 SIGSEGV，pc = `.ncr+0x5bc8`，`x20=0x48416df089015220`、`x22=0x926fe538d8d6e746` **全是垃圾值** |
| **根因** | 两套 VMP 用相同段名（`.ncq,.ncs`），链接进同一 so 后混在一起。`.ncs` 里 129 个 `R_AARCH64_RELATIVE` 重定位的 addend **全部**指向 `.text`（第二套的 handler 表），第一套的表被挤掉 |
| **连锁** | `.ncr` 里的第一套解释器按 `adr` 偏移找表 → 找到第二套的 → VM 寄存器读到垃圾 → SIGSEGV |
| **修法** | 段名按套分开：第一套 `.ncq`/`.ncs`，第二套 `.ncv`/`.ncw` |
| **教训** | 两套看似独立的机制，**共用某个全局命名空间一定会在链接期冲突** |

## K-07 段名重复导致同一段被加密两次

| 项 | 内容 |
|---|---|
| **文件** | `protect.sh`（`_SECTIONS` 拼接） |
| **症状** | 真机 SIGILL，pc = `.ncx+0x8f78`，解锁前 `.ncx`/`.nct` 保持密文 |
| **根因** | 字符串拼接写错：<br>`_SECTIONS=".nct,$_SECTIONS"`（已含 `.nct`）<br>再 `_SECTIONS=".nct,.ncv,$_SECTIONS"` → **`.nct` 出现两次** |
| **后果 ①** | `.nct` 被 RC4 加密两次 = **还原成明文** |
| **后果 ②** | MAC 输入把 `.nct` 密文拼了两遍 → 与运行期算的对不上 → 返回 -11 → 解锁中止 |
| **铁证** | 用产物反算 MAC：旧段序 `[.nct,.ncv,.nct,.ncx,.ncxr]` → 匹配 ✅；正确序 `[.nct,.ncv,.ncx,.ncxr]` → 不匹配 ❌ |
| **修法 ①** | 改用数组 `_SEC_ARR+=()` —— 每个段只 append 一次，不可能重复 |
| **修法 ②** | 加断言 `sort \| uniq -d`，有重复直接 `exit 1` |
| **教训** | 这类 bug 的症状**永远不指向真因**：RC4 两次 = 明文、MAC 拼两遍 = 校验失败，叠加后表现为"执行密文 SIGILL" |

## K-08 retain 缺失导致自检函数被 gc

| 项 | 内容 |
|---|---|
| **文件** | `nc_guard_probe.c`（`ncg_key_slot`）+ `nc_guard_jni.c`（`nc_link_jni_selftest`） |
| **症状** | 构建全绿、判决与心跳照常，只是 selftest 永远 `UnsatisfiedLinkError` |
| **根因 ①** | `ncg_key_slot` 无引用 → `--gc-sections` 把整个 `.nck` 段回收 |
| **根因 ②** | 动态注册后 `nc_link_jni_selftest` 没有任何直接调用者（下游只有 weak 引用，weak 不构成强依赖）→ 被 gc |
| **实测** | 不加 retain 时 `llvm-nm libnc.so \| grep selftest` 无输出；加后符号存在（`SHF_GNU_RETAIN`） |
| **修法** | 两者都加 `used, retain`。**在消费方给 extern 声明加无效**（属性只对定义生效） |
| **同类病** | 报错四十九（自检类没生成、异常被吞）—— 都是"假绿" |

## K-09 单文件源清单漏改（一天内踩四次）

| 项 | 内容 |
|---|---|
| **文件** | `test.sh` / `make-zip-lib.sh` / `nox` CLI / `protect.sh` |
| **症状** | `dlopen` 报 `cannot locate symbol: ncg_report_flush`，而 `boot.c` 明明引用了它 |
| **根因** | 四处独立维护的 `.c` 清单，新增一个 `.c` 时漏改任一处 |
| **为什么难查** | 分 TU 编译不报错（各 `.c` 各自编 `.o` 都成功），**只在链接后 dlopen 才炸**，且报错只说 `undefined symbol`，不指向清单本身 |
| **修法** | `test.sh` 改通配符（排除 `nc_guard_jni.c` —— 要 NDK 的 `jni.h`）；`make-zip-lib.sh` 的 `LIB_SRCS` 保留显式（生产清单，含 jni）；`nox` CLI 改扫描；`protect.sh` 加 `for` 兜底 |
| **新增断言** | V14（三条）：每个 `.c` 都在生产清单里 + `test.sh` 仍是通配符 + `nox` CLI 仍是动态扫描 |
| **教训** | **断言比记忆可靠** |

## K-10 报告缓冲撑大 .bss → SIGILL

| 项 | 内容 |
|---|---|
| **文件** | `nc_guard_report.c`（报告缓冲） |
| **症状** | 加了自检报告后真机 SIGILL，pc 落在 `.ncx` 里，寄存器全是垃圾 —— **完全不指向"多了一个全局数组"** |
| **根因** | 缓冲第一版 `static char s_buf[4096]` → `.bss` 从 2312B 涨到 3864B → `.ncxhr`（master，32B）与 `.bss` 的页面归属改变 → `ncg_page_has_writable_neighbor()` 判定变 → SIGILL（rc=132） |
| **修法** | 缓冲放**栈上**，由调用方传入（报告约 1.2KB，栈承受得起） |
| **同类** | K-01 的第三次复发 |

## K-11 JNI 符号隐藏的上限

| 项 | 内容 |
|---|---|
| **文件** | `nc_guard_jni.c` + 消费方 `lib-ndk.sh` 的 version script |
| **症状** | 外部报告给"符号表处理"打 0.0 分（`nm -D` 看到 `Java_xxx` 带地址与大小） |
| **根因** | version script 被包在 `if [ -f "$jni/nc_jni_gen.c" ]` 里，而该文件的生成器已在 `a7d9cbc`（动态注册真机崩）连同一起删除 → **condition 恒假 → version script 从未生效过**。而 `--strip-all` 只删 `.symtab/.strtab`，删不掉 `.dynsym` |
| **修法** | 拆掉 guard + 白名单 `Java_*` + 补 `-Wl,--undefined-version` |
| **边界 ①** | `-fvisibility=hidden` 本身已隐藏普通内部符号，version script 的新增收益只是挡住 `visibility("default")` 强行导出的运行时符号（实测 3 个） |
| **边界 ②** | **「隐藏 JNI 符号」与「短名绑定」不可兼得** —— `Java_*` 必须在 `.dynsym` |
| **边界 ③** | 想真正隐藏只有动态注册，而动态注册在 so 加载时机（Application 初始化中）会崩 |
